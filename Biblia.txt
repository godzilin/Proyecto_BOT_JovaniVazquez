# Biblia del proyecto: bot de Discord

Este documento define la estructura, los límites y las normas técnicas del bot. Debe consultarse antes de añadir funcionalidades o cambiar la arquitectura. Las decisiones de producto (nombre, funciones, permisos y persistencia definitiva) se concretarán cuando se definan los requisitos.

## 1. Objetivo y principios

El proyecto será un bot de Discord desarrollado en Python, organizado para que sus funciones puedan crecer sin convertir el punto de entrada en un bloque monolítico.

Principios obligatorios:

1. **Simplicidad antes que infraestructura:** no añadir capas, servicios ni dependencias sin una necesidad concreta.
2. **Responsabilidades separadas:** Discord, lógica de negocio, configuración y persistencia no deben mezclarse.
3. **Asincronía de extremo a extremo:** no bloquear el event loop con operaciones de disco, red o cálculos prolongados.
4. **Seguridad por defecto:** secretos fuera del código y permisos mínimos para el bot.
5. **Fallos visibles:** registrar y comunicar los errores de forma útil; no ocultarlos ni convertirlos en éxitos falsos.
6. **Cambios verificables:** toda funcionalidad nueva debe incluir pruebas adecuadas y documentación cuando cambie el uso o la configuración.
7. **Compatibilidad con Discord:** respetar límites de tasa, intents, permisos y políticas de la API.
8. **Código documentado:** todo archivo del proyecto debe dejar claro para qué existe y toda lógica no trivial debe estar explicada de forma útil y mantenible.

## 2. Tecnologías y convenciones

- **Lenguaje:** Python 3.12 o superior, salvo que el entorno de despliegue requiera una versión distinta. La imagen del NAS usa 3.13 y el entorno local debe usar la misma.
- **Librería de Discord:** `discord.py` 2.x. Usar sus comandos de aplicación (slash commands) como interfaz principal.
- **Gestión de dependencias:** mantener las dependencias directas y sus versiones en `pyproject.toml`; usar un lockfile si el gestor elegido lo genera.
- **Estilo:** seguir PEP 8, usar anotaciones de tipos en interfaces y funciones públicas, y preferir nombres descriptivos en inglés en el código.
- **Idioma visible:** mensajes, ayuda y textos destinados a usuarios se definirán en español, salvo que se acuerde internacionalización.
- **Formato y análisis:** configurar un formateador y un linter (por ejemplo, Ruff) en el proyecto; no introducir herramientas duplicadas sin motivo.
- **Interfaz del bot:** preferir interacciones y respuestas efímeras cuando el contenido sea privado o solo relevante para quien ejecuta el comando.
- **Documentación del código:** documentar cada archivo, módulo, clase y función pública según las normas de la sección 8.1.

Node (`package.json` de la raíz) solo se usa para pintar las escenas de canvas sin navegador (`bot.services.node_scene`); el bot sigue siendo Python.

No fijar versiones de paquetes al azar ni añadir una dependencia para una tarea que pueda resolverse claramente con la biblioteca estándar o con herramientas ya instaladas.

## 3. Estructura de referencia

```text
.
├── src/
│   └── bot/
│       ├── __init__.py
│       ├── __main__.py          # Inicio ejecutable: python -m bot
│       ├── app.py               # Construcción y ciclo de vida del cliente
│       ├── config.py            # Lectura y validación de configuración
│       ├── logging_config.py    # Configuración común de logs
│       ├── cogs/                # Comandos y eventos agrupados por dominio
│       │   ├── __init__.py
│       │   └── ...              # Ej.: general.py, moderation.py
│       ├── services/            # Casos de uso y lógica de negocio
│       ├── repositories/        # Acceso a datos, si la persistencia lo requiere
│       ├── models/              # Tipos y modelos compartidos, si son necesarios
│       └── utils/               # Utilidades pequeñas, genéricas y reutilizables
├── tests/
│   ├── unit/
│   └── integration/
├── .env.example                # Nombres y ejemplos no secretos
├── .gitignore
├── pyproject.toml
└── README.md
```

La estructura es una guía, no una obligación de crear carpetas vacías desde el primer día. Añadir un módulo cuando exista una responsabilidad real que ubicar en él. No crear un directorio genérico para una única función trivial.

## 4. Límites y responsabilidades

### Punto de entrada y aplicación

- `__main__.py` inicia el proceso y delega la construcción y ejecución del bot.
- `app.py` configura el cliente, registra extensiones y gestiona el arranque y cierre ordenados.
- El token no se escribe ni se proporciona como literal en estos archivos.
- El arranque debe fallar claramente si falta una configuración obligatoria.

### Configuración

- `config.py` es el único lugar que interpreta variables de entorno y valida su formato.
- La aplicación recibe una configuración validada; los módulos no deben leer variables de entorno dispersas.
- Mantener `.env.example` actualizado con los nombres requeridos y valores ficticios. No guardar `.env` en el repositorio.
- Separar configuración local de producción; no introducir secretos en argumentos, logs, capturas ni mensajes de error.

### Cogs y comandos

- Cada cog agrupa comandos y eventos de un mismo dominio funcional; evitar un cog único que crezca sin límite.
- Los cogs adaptan las interacciones de Discord a llamadas de servicios. No alojan reglas de negocio complejas ni consultas de persistencia extensas.
- Validar entradas, permisos y contexto en el límite del comando. Comprobar los permisos requeridos también en Discord cuando corresponda.
- Responder a las interacciones dentro de los plazos de Discord (3 segundos); diferir la respuesta antes de trabajo que pueda tardar. En botones, menús y formularios: `ack(interaction)` de `bot.utils.interactions` antes de tocar la base de datos, dibujar, llamar a la API de Discord o esperar un candado, y después `edit`/`notify`. Solo lo que cambia memoria contesta directamente. Los botones que se rehacen en cada jugada llevan `custom_id` fijo, para que el rescate de clics del cog `Errors` encuentre su sustituto. Reglas completas en «Botones rápidos» de CLAUDE.md; `tests/integration/test_button_speed.py` lo comprueba con el bot real.
- Dar respuestas de error claras y seguras. No mostrar trazas, tokens ni datos internos a usuarios.
- Registrar listeners con moderación: evitar trabajo repetido por cada evento y evitar respuestas o efectos duplicados.
- Ayuda: `/ayuda` es un menú desplegable, como el de `perfil`: una portada con las categorías y una página por categoría con cada comando en orden alfabético y su descripción de slash command (sin argumentos). Las categorías salen de `HELP_CATEGORIES` (por cog) y `COMMAND_CATEGORIES` (por comando, cuando un cog mezcla temas) en `bot.cogs.general`; un comando nuevo entra en una existente afín antes que en una nueva de un solo comando. Los efectos de imagen van en bloque, solo por nombre, en la página de Imagen.
- Comandos de administración (cog `Admin`): solo para miembros con el permiso Administrador, comprobado en el servidor en cada uso (`cog_check` e `interaction_check`), no solo con `default_permissions`. La categoría Admin de la ayuda solo se muestra a administradores.
- Nombres de comandos: cortos (máximo 8 caracteres), de una sola palabra, reconocibles y consistentes entre sí. Cada comando tiene UN único nombre, idéntico en su versión de aplicación (`/poner`) y en su versión de texto con prefijo (`.poner`). Sin alias que cambien el nombre según la interfaz, sin grupos ni subcomandos y sin variantes duplicadas "cortas/largas": el menú de `/` debe quedarse limpio. La ayuda (`/ayuda`) se genera desde los comandos registrados y los lista una sola vez.
- Idioma de los nombres de comandos: **todos en español**, en la palabra que usaría cualquiera en España (`/poner`, `/cola`, `/saltar`, `/echar`, `/ranking`), nunca la inglesa (`/play`, `/queue`, `/kick`). Si la palabra natural pasa de 8 caracteres, se busca otra española que quepa (`indultar` en vez de "desbanear", `tragas` en vez de "tragaperras", `cohete` para el Crash). Solo conservan el nombre original los juegos que en España se llaman así (`blackjack`, `pachinko`, `bizum`, `backgammon`) y los comandos de imagen de la excepción de abajo (`magik` y los efectos de Dank Memer). Al renombrar un comando se actualizan en el mismo cambio sus menciones en textos del bot, docstrings, pruebas, README y FUNCIONALIDADES. Esto solo afecta a lo que ve el usuario: el código interno (funciones, variables, clases) sigue en inglés según la sección 2.
- Funciones puente entre cogs (`achievements.track`, `renta.remind`, `shop.xp_multiplier`…): buscan el cog con `bot.utils.cogs.find_cog(bot, Clase)`, nunca con `isinstance(cog, Clase)`. `load_extension` vuelve a ejecutar el módulo de cada extensión, así que quien lo importó antes ve otra clase y el `isinstance` falla en silencio (así se perdieron los logros del casino). `tests/integration/test_cog_bridges.py` lo comprueba con el bot cargado de verdad: una función puente nueva se añade ahí.
- Excepción, los comandos de imagen: son **solo de texto** (`.magik`, `.memes` y los efectos de Dank Memer), porque Discord limita un bot a 100 slash commands y los efectos son más de 100. Los efectos conservan el nombre que tienen en Dank Memer aunque pase de 8 caracteres (`.changemymind`), y `/ayuda` los reparte en subcategorías de Imagen según su tipo (`Command.extras["help_group"]`). `.memes <efecto>` explica cada uno. El resto de la norma (sin alias, sin grupos, un nombre por comando) se mantiene.
- Excepción, el blackjack: se llama `blackjack` (`/blackjack` y `.blackjack`, aunque pase de 8 caracteres) y tiene el atajo de texto `.bj`. Junto con `.met` de `reinicio`, es el único alias permitido; el menú de `/` solo muestra `/blackjack`.
- Todas las tragaperras van en `tragas`, que elige la máquina (la clásica o una de Botes, `MACHINE_CHOICES` de `bot.cogs.slots`): una máquina nueva de `hold_win.THEMES` sale sola como opción y no lleva comando propio.
- Lo de cada miembro va en `perfil`, un solo comando con un desplegable de secciones (nivel, patrimonio, trabajo, logros, rachas y objetos), en vez de un comando por cosa: el menú de `/` se queda limpio. Cada sección la pinta el cog dueño de los datos (`level_embed`, `patrimonio_embed`, `work_embed`, `build_view`, `backpack_embed`) y `perfil` la pide con `find_cog`. Algo nuevo que enseñe datos de un miembro entra como sección (caben 25) y su clave se añade a `PERFIL_SECTIONS`, que cuenta el logro «Expediente completo». Lo que se hace (fichar, comprar, jugar) sigue en su comando.
- Excepción, el patrimonio: `patrimonio` (`/patrimonio` y `.patrimonio`) enseña sola la sección 🏰 Patrimonio de `perfil` (el mismo `patrimonio_embed`), aunque pase de 8 caracteres y repita una sección, porque es el nombre del impuesto y lo pidió así el proyecto. Sin alias ni subcomandos: el miembro es una opción.
- Excepción, la beernight: `beernight` pasa de 8 caracteres y no está en español porque es el nombre del evento del servidor y lo pidió así el proyecto. No tiene alias ni subcomandos: todo va en su panel, y subir un audio son dos opciones del mismo comando.
- Excepción, `robuso` (administración): se llama como el miembro del que apunta si está en Hong Kong o en Madrid, para los logros de su categoría secreta; como `hongkong`, es un nombre propio y no hay palabra española mejor.
- Excepción, `jovani`: es un nombre propio, como `hongkong` o `robuso`: la ficha del bot. Sus datos solo son totales del servidor (`bot.services.aspecto.facts`), nunca quién ha hecho qué.
- El perfil del bot (cog `Aspecto`) va por servidor y nunca toca el global. Un look nuevo es una fila en `BUILTIN_LOOKS` con un sitio en `automatic_look`, y sube la meta de `jovani_looks_12`. Los límites de cambiar el perfil no se escriben como si fueran de Discord, que no los publica: `MIN_PROFILE_SECONDS` es una decisión del proyecto y lo que manda Discord se respeta con `blocked_until`.
- Excepción, el backgammon: se llama `backgammon` (`/backgammon` y `.backgammon`), aunque pase de 8 caracteres, porque en España el juego se llama así y lo pidió así el proyecto. Sin alias ni subcomandos: retar a alguien es una opción del mismo comando.

### Servicios

- `services/` contiene los casos de uso y las reglas de negocio, independientes de detalles de presentación de Discord siempre que sea práctico.
- Los servicios reciben dependencias explícitas; no crean clientes globales ni leen configuración directamente.
- No duplicar reglas entre comandos. Extraerlas cuando más de una funcionalidad las necesite o cuando su complejidad lo justifique.

### Dinero, impuestos y la Renta

El dinero del bot (yapdollars) imita la economía española: todo lo que se gana o se gasta tiene tratamiento fiscal y Hacienda (Perro Sanxe) está presente. Cualquier funcionalidad nueva que mueva dinero (juegos, tienda, trabajos, premios, transferencias entre usuarios…) debe cumplir estas reglas:

1. **Solo a través de `EconomyService`** (`bot.economy`). Nunca tocar `economy_wallets` ni `economy_ledger` desde otro sitio. Cada movimiento lleva un motivo corto y estable (`"juego:apuesta"`, `"tienda:compra"`).
2. **Decidir y documentar su tratamiento fiscal.** En la docstring del método que mueve el dinero, indicar cuál de estos aplica y por qué, citando la norma real (ley y artículo) en la que se inspira:
   - Renta sujeta a IRPF con retención: `EconomyService.pay_income` (p. ej. premios por nivel).
   - Juego: `settle_bet`, o `place_bet` + `pay_winnings` si el resultado llega después. Así entra en la retención diaria del casino (el 19 % fijo del neto positivo de cada día que pase de `taxes.GAMBLING_EXEMPT`) y en la declaración de los lunes.
   - Exento: un método sin retención (p. ej. el IMV, art. 7.y LIRPF). Exento no significa olvidado: hay que justificarlo con la norma que lo exime, no con una analogía.
   - Otro impuesto: las reglas van en `services/taxes.py` y el cobro en el repositorio de economía, dentro de la misma transacción que el movimiento. Las compras pagan **IGIC** (`taxes.igic`), nunca IVA: el servidor es canario. El tipo general es el 7 % (art. 51 de la Ley 4/2012 de Canarias) y la tienda deja elegir por artículo entre los tipos de `taxes.IGIC_RATES` (cero, 3 %, 7 %, 9,5 % y 15 %). Las compras se cobran con `EconomyService.purchase`, que manda la base a la caja de la tienda y el IGIC al Estado. Sucesiones y Donaciones solo se aplica a dinero que pasa de un miembro a otro; lo que regala el bot (cumpleaños, saludos, premios) es una ganancia patrimonial y va por `pay_income` (art. 33.1 LIRPF).
   - Bizum entre miembros (`EconomyService.bizum`): es el único camino del dinero de un miembro a otro y está **exento** de Sucesiones y Donaciones por decisión del proyecto, para no asfixiar a impuestos los pagos entre colegas. Es una excepción consciente a «exento no es una analogía»: en la vida real sería una donación sujeta (art. 3.1.b de la Ley 29/1987) y Canarias solo la bonifica al 99,9 % para los grupos I y II (art. 26 sexies del Decreto Legislativo 1/2009); el bot trata a todo el servidor como grupo II. Sin IRPF para quien recibe (art. 6.4 LIRPF). Detalle en `bot.services.bizum`.
   - Rastro, la segunda mano entre miembros (`EconomyService.market`, reglas en `bot.services.rastro`): quien compra paga el **ITP** de los bienes muebles de Canarias, 5,5 % (art. 31.1.d del Decreto Legislativo 1/2009; `taxes.itp`), nunca IGIC, porque quien vende es un particular (art. 4 de la Ley 20/1991). La base es el **mayor entre el precio y el valor de referencia** (el precio de catálogo del artículo, como las tablas con que Hacienda comprueba el valor de un coche usado: art. 10.1 del RDL 1/1993 y art. 57.1.b LGT), así que vender a 1 Y$ no baja el impuesto. La parte regalada (precio por debajo del valor) está **exenta** de Donaciones por decisión del proyecto, como el Bizum. Quien vende por más de lo que le costó paga el **19 % de la plusvalía** (art. 33.1 LIRPF, primer tramo del ahorro; `taxes.capital_gain_tax`), descontado de lo que cobra y sin liquidación posterior. Lo que cuesta un objeto es lo pagado en la tienda sin IGIC, o, si se compró en el Rastro, el mayor entre precio y valor más el ITP (arts. 35.1.b y 36 LIRPF). Las pujas esperan con su ITP en el depósito del Rastro (`MARKET_ACCOUNT_ID`) y se devuelven enteras a quien es superado. ITP y plusvalía van al Estado y a `economy_market_tax`; `hacienda` los cuenta como «ITP» y en el «IRPF del ahorro». El **trueque** (`trueque`, `rastro.Swap`) es una permuta: cada uno paga el ITP de lo que recibe sobre su valor de referencia (art. 23 del RDL 1/1993; quien añade dinero, sobre el mayor entre valor y dinero) y el 19 % de la ganancia de lo que entrega, que es el mayor entre su valor y el de lo recibido menos lo que le costó (art. 37.1.h LIRPF); el dinero que se añade cuenta para quien lo cobra. Las dos mitades se pagan en la misma transacción (`MarketMove.payments`). **El freno para no tener sin ganárselo lo que pide esfuerzo no es un impuesto:** quien compra tiene que cumplir el nivel mínimo y el límite por persona del artículo, igual que en la tienda.
   - Monte de Piedad (panel de `vender`, `EconomyService.monte`, reglas en `bot.services.monte`): compra y presta con la **caja de la tienda** (`SHOP_ACCOUNT_ID`), así que no crea ni destruye dinero: lo gastado en la tienda vuelve a circular, y nunca más de lo gastado. Paga una parte de **lo que se pagó por esa unidad en la tienda** (sin IGIC y con su rebaja; lo comprado en el Rastro vale la venta original de la tienda): el 85 % al venderlo y el 55 % prestado al empeñarlo, que se devuelve con un 5 % en 3 días o el objeto se queda en el Monte. No acepta lo que no salió de la tienda (cajas ganadas jugando, regalos, `crear`) ni lo numerado: con el precio de catálogo, las rebajas de hasta el 90 % y la 📦 gratis del casino (un 9,5 % de lo apostado a catálogo) habrían sido máquinas de hacer dinero (`docs/monte_sim.py`). Vender es una transmisión siempre por debajo de lo que costó: sin ganancia no hay IRPF (art. 34 LIRPF) y la pérdida no se computa, como en el Rastro; es un cobro y paga el embargo de Hacienda. El empeño es un préstamo con prenda: no es renta, exento de ITP y AJD (art. 45.I.B.15 del RDL 1/1993) y no se embarga, como el Bizum de mamá; el interés, exento de IGIC (art. 18 del Decreto Legislativo 1/2025 de Canarias). Los topes de las cifras los comprueba `tests/unit/test_monte.py`: el préstamo no pasa del 70 % de la venta (si no, empeñar y no volver esquivaría el embargo) y el interés pesa más que el Patrimonio que se ahorraría empeñando el domingo.
   - Patrimonio: lo cobra cada lunes `bot.cogs.patrimonio` sobre el saldo, los inmuebles de `pisos` a su valor fiscal (`repositories.housing.assets_in`) y los objetos de la tienda (`repositories.shop.wealth_goods_in`, arts. 18 y 19 de la Ley 19/1991), a la escala general (mínimo de 7.000.000 Y$), con el límite conjunto con el IRPF de esa misma semana (art. 31, `taxes.wealth_quote`): la cuota del IRPF y la del Patrimonio no pasan juntas del 60 % de la base del IRPF de la semana (ahorro incluido), la parte de los objetos no se rebaja y la rebaja no pasa del 80 % de la ley (`WEALTH_MAX_REDUCTION`): siempre se paga al menos el 20 %. Se usa la base y la cuota de la semana, no las de un año: la semana es el año fiscal. Quien pasa de 37.000.000 Y$ declara el Impuesto de Solidaridad de las Grandes Fortunas (art. 3 de la Ley 38/2022) en `economy_solidarity_tax`: descuenta el Patrimonio y en Canarias sale a cero, pero se apunta y `hacienda` lo enseña. No hay que hacer nada en cada acción. Lo que no llega en efectivo queda en `economy_tax_debts` y `EconomyRepository.housing` lo embarga de lo que cobre el miembro por sus pisos (art. 169 de la Ley 58/2003), en la misma transacción.
   - Pisos (`EconomyService.housing`, reglas en `bot.services.housing`): comprar paga el ITP de los inmuebles de Canarias (6,5 %, art. 31 del Decreto Legislativo 1/2009) y una notaría que desaparece salvo su IGIC del 7 % (servicio profesional, art. 51 de la Ley 4/2012), que va al Estado. La renta de cada noche es rendimiento del capital inmobiliario (art. 22 LIRPF) y se apunta por inmueble (`economy_tax_records` con su `ref`): los intereses y las reparaciones restan como mucho lo que ingresa ese inmueble y el resto se arrastra 4 semanas (art. 23.1.a, «4 años»); IBI, comunidad, seguro y amortización (3 % de la construcción, art. 14 RIRPF) sí pueden dejarlo en negativo, y el negativo rebaja el resto de la base (art. 48: desgravar la hipoteca); sobre el neto positivo de la vivienda se aplica la reducción del art. 23.2 (Ley 12/2023: 90 % en zona tensionada con un contrato nuevo que baja la renta más de un 5 %, 50 % el resto; locales, garajes, vacacional y nómadas, nada), fijada al firmar el contrato (`housing.contract_reduction`). Cada noche retiene con el tipo estable de la semana y el lunes la declaración liquida. Los pisos vacíos imputan el 1,1 % anual del catastral por día vacío (art. 85, nunca la vivienda habitual). El IBI va al Estado y la comunidad desaparece; vender paga la agencia (con su IGIC del 7 %) y el 19 % de la ganancia. Lo que no cubre la renta se cobra del monedero de los dueños hasta donde llegue (`HousingDebit`) y el resto queda como deuda del piso. El índice de cada barrio sube y baja por el mismo factor al comprar y vender, ponderado por lo que pesa el inmueble, y cada noche se acerca a lo que tienen comprado los miembros (`housing.ownership_level`): un barrio acaparado se encarece y se tensiona. Comprar el barrio entero lo sube un 10 % (`INDEX_STEP`), menos que el ~11 % de una ida y vuelta (ITP, notaría y agencia con su IGIC): inflarlo con idas y vueltas, o comprando algo pequeño para encarecer lo que ya se tiene, nunca sale a cuenta. El tope de «Nada crece sin tope» son los 180 inmuebles del catálogo y las 20 promociones de obra nueva del servidor (uno de cada): no hay más que comprar aunque se reinviertan las rentas.
   - Pisos, fases 2 a 4 (tratamiento en el docstring de `EconomyService.housing`): la hipoteca se crea de la nada y sus cuotas desaparecen (el banco no existe), sus intereses se restan de la renta de ese inmueble con el tope y el arrastre de la regla anterior (art. 23.1.a LIRPF) y la ejecución subasta al 70 % (art. 671 LEC) y deja deuda con el banco; la VPO no paga impuesto por la vivienda (IGIC al tipo cero de las VPO, art. 52 de la Ley 4/2012) pero sí el IGIC del 7 % de su notaría, y su precio va al Estado, que la recompra al mismo precio; lo pagado por la hipoteca de la vivienda habitual desgrava en la declaración (canaria, art. 14 del DL 1/2009); la renta de un miembro inquilino la paga su monedero, el casero la cobra con el IRPF de siempre y el inquilino desgrava (canaria, art. 15); el Bono Alquiler Joven sale de la cuenta del Estado (si llega) con retención de IRPF; la estancia vacacional lleva dentro el IGIC del 7 % y la licencia es una tasa, los dos al Estado; cada estancia paga además la plataforma (15 %) y la limpieza, que desaparecen salvo su IGIC del 7 % (al Estado) y restan en el IRPF como servicios de terceros (art. 13.d RIRPF); lo que aprueba la junta de copropietarios lo pagan todos los dueños según sus participaciones con el tratamiento de siempre (la reforma y la licencia, con sus impuestos), la derrama al fondo de reserva desaparece (lo que no se paga queda como deuda del piso) y el fondo es un número del inmueble, no una cuenta: la comunidad ya desaparecía; la acción de división vende con los impuestos de una venta entre miembros (o al mercado, si nadie puja); la SOCIMI cambia el IRPF del alquiler por el 19 % del dividendo. Todo lo que paga el Estado (VPO recomprada, bono) solo se paga si su cuenta llega: nunca se crea dinero en su nombre.

Lo que paga el seguro de impago se crea de la nada (sustituye a la renta: rendimiento del capital inmobiliario); para que no sea un grifo, la prima se calibra para que la aseguradora gane (paga de media un 75-83 % de lo que cobra, `housing.PREMIUM_CURVE`) y solo cubre a quien pasa el estudio de solvencia. El abogado y el procurador del desahucio desaparecen, con su IGIC al Estado, y son gasto deducible del inmueble (art. 13.c RIRPF, `HousingMove.expenses`). Las deducciones canarias del casero (arts. 15 ter, 15 quater y 16 del Decreto Legislativo 1/2009) van en la declaración, una por inmueble, la mayor (art. 18); la del art. 16 la controla `pisos` (una vez por inmueble y cinco por persona, `housing_rent_bonus`). Lo que no se puede pagar de esos impuestos se debe con el IBI del piso. Elegir inquilino no mueve dinero: la gestora elige al azar y deja el impago, las marchas y las averías en la media de antes (`housing.tenant_factors`).
   - Pisos, compraventa entre miembros (8.2.0, `HousingRepository.member_sale` y las subastas): es otro camino del dinero de un miembro a otro, con sus impuestos, como el Rastro. El comprador paga al vendedor el precio y el ITP de los inmuebles (6,5 %; 7 % en las subastas judiciales, art. 31.f del DL 1/2009) sobre el mayor entre el precio y el valor de referencia (90 % del de mercado), y la notaría con su IGIC; el vendedor, el 19 % de la ganancia con el mayor entre el precio y el valor de mercado (en una subasta, el precio). La parte regalada va exenta de Donaciones por decisión del proyecto. Las pujas esperan con su ITP y su notaría en el depósito de las subastas (`HOUSING_AUCTION_ACCOUNT_ID`) y se devuelven enteras a quien superan: no se crea ni se destruye nada. La hipoteca del comprador la presta el banco (se crea) como en cualquier compra. El tope contra la reventa es que lo adjudicado en una subasta judicial no se vende al mercado en 30 días.
   - Pisos, reformas e imprevistos (8.3.0): la obra de una reforma desaparece (la empresa no existe) y su IGIC (7 %), el ICIO (4 %, art. 102 del RDL 2/2004) y la tasa de la licencia van al Estado; es una mejora (art. 35.1.b LIRPF), no un gasto, así que suma a lo pagado del inmueble (Patrimonio y amortización) y a su coste (ganancia al vender). Sube el valor del inmueble el 60 % de lo que cuesta, con tope: reformar para vender pierde, no hay bucle. Las reparaciones de los imprevistos que decide el dueño se pagan con el cierre de la noche, con su IGIC; la franquicia del parte al seguro desaparece y recarga la prima del hogar (con su impuesto de primas).
   - Pisos, plantas y habitaciones (9.12.0): la obra de dividir por plantas desaparece y su IGIC (7 %), el ICIO (4 %), la tasa de la licencia de obra y el AJD de la escritura de división horizontal (0,75 % del valor del inmueble, art. 36 del D. Leg. 1/2009; clase `ajd`, que `hacienda` cuenta con el ITP de los pisos) van al Estado; los muebles de las habitaciones desaparecen y su IGIC va al Estado. Las dos son una mejora, como una reforma: suman a lo pagado y al coste del inmueble. Las plantas valen lo que el entero más el 60 % de la obra (dividir para vender pierde). La renta de cada planta o habitación tributa como la de cualquier inmueble; la de una habitación es vivienda si quien la alquila vive ahí (DGT V0412-2025), salvo la de los nómadas. Una habitación paga su parte de la amortización y de los intereses de la hipoteca del piso, no la entera.

No se crea ni se destruye nada. El aval de los padres (favor de `pala`) no mueve dinero: solo cambia lo que mira el banco (`housing.parents_income`) y la garantía. La obra nueva tiene su tope: una promoción por barrio.
   - Pisos, duración y recuperar el piso (9.23.0, `docs/pisos-llaves.md`): elegir la duración, no renovar, la prórroga y pedirlo para vivir no mueven dinero. Comprar las llaves a un inquilino del catálogo desaparece (no existe), sin IGIC (quien cobra es un particular, art. 4 de la Ley 20/1991), y para el casero es una mejora, no un gasto deducible (DGT V3259-23): suma a lo pagado y al coste de su parte, como una reforma. Comprárselas a un miembro pasa del casero al miembro, que tiene una ganancia patrimonial de la base del ahorro (arts. 33.1 y 49 LIRPF, DGT V3259-23): sin retención en la ley, aquí se le descuenta el 19 % al cobrarla (`plusvalia`), como en el Rastro. La indemnización del art. 9.3 LAU (irse antes de vivir 12 días en lo pedido para vivir) va igual, pero no es una mejora. Para que echar a alguien no sea un grifo, el inquilino pide además la mitad de lo que le costaría de más alquilar otro igual si los alquileres han subido (`housing.KEYS_MARKET_SHARE`) y la fama de casero encarece cada piso recuperado en 30 días: subirle la renta así solo compensa si el barrio se ha disparado (`docs/pisos_sim.py --duraciones`). En la ley, un contrato de menos de 5 años lo prorroga el inquilino hasta los 5 (art. 9.1 LAU); el juego deja que dure lo firmado (decisión del proyecto).
   - Préstamos personales (`banco`, reglas en `bot.services.loans`, tratamiento en el docstring de `EconomyService.housing`): el banco de las hipotecas, que no existe (lo prestado se crea y las cuotas, la comisión de apertura y las primas desaparecen); un día es un mes y la cuota se cobra en el cierre de cada noche de `pisos`. **Las cuotas de hipotecas y préstamos juntas no pasan del 35 % de los ingresos** (`housing.affordable` con `Market.installments_of`). Exento de ITP y AJD y de IGIC; los intereses no se deducen; la deuda resta en el Patrimonio. El seguro de protección de pagos lleva el IPS del 8 % al Estado y lo que paga no mueve dinero. Con deuda con Hacienda no se presta (lo prestado se embargaría al entrar). Quien no paga entra en el fichero de morosos (`loans.in_asnef`: ni préstamos ni hipotecas) y, con 3 cuotas seguidas, el préstamo vence y pasa a la deuda con el banco, que se cobra cada noche y se embarga de las nóminas (regla 6). Es crédito, no una fuente de dinero: se devuelve con intereses (el sumidero). La **financiación de compras** (💳 Financiar, 9.20.0, `bot.services.credit` y `docs/financiar.md`) es un préstamo más (`kind` `compra` o `plazos`) atado a una compra: lo prestado (la compra más su comisión) entra y la compra se paga en el acto por su camino de siempre; si falla, se deshace. Sigue las mismas reglas (35 %, fichero de morosos, vencimiento, embargo) salvo Paga en 3, que no mira el 35 % al firmar. Toda compra nueva de un bien o un servicio ofrece 💳 Financiar (`banco_compras.Deal`), menos lo emblemático (numerado o títulos), el juego, impuestos y tasas, depósitos y compras entre miembros. Lo financiado sin devolver sube los precios de la tienda y las obras (el **IPC del crédito**, `credit.ipc`, hasta el 20 %): un precio nuevo de la tienda o de `pisos` lo lleva encima y se recalcula solo en momentos fijos (`refresh_ipc`). La **rehipoteca** (🔐 Garantías, 9.1.0, `docs/garantias.md`) es una hipoteca más de `housing_mortgages` (`kind = 'rehipoteca'`): lo prestado se crea, la tasación desaparece salvo su IGIC (al Estado), sus intereses no se deducen de la renta del piso (art. 23.1.a.1.º LIRPF) y su cuota no desgrava como vivienda habitual. Todas las hipotecas de alguien sobre un inmueble se ejecutan juntas, con una sola subasta. Con `docs/economia_sim.py` (estrategia «hipoteca y rehipotecas») el Falcon sigue en el mismo día: rehipotecar solo compite con la hipoteca de compra por el 35 %. El **anticipo de rentas** (💸 Anticipos, 9.2.0) es un préstamo más de `housing_loans` (`kind = 'rentas'`, con su inmueble): lo adelantado (el valor actual de 3, 6 o 12 meses de tu parte de la renta) se crea y la comisión desaparece; no es renta, la renta sigue tributando cada noche al devengarse (art. 14.1.a LIRPF) y su coste no deduce (art. 23.1.a.1.º). No mira el 35 % al firmar, pero su cuota cuenta después; no cuenta en el tope de préstamos personales, y con uno vivo no hay venta voluntaria del inmueble (las forzosas siguen y el anticipo también). El **avalista** (9.3.0) no mueve dinero al firmar: suma su hueco del 35 % y baja el tipo, y la cuota avalada cuenta en su 35 % mientras dure. Si el avalado no paga, el banco reclama al avalista (su deuda con el banco, regla 6) y el avalado le debe lo pagado (`housing_member_debts`, art. 1838 CC): ese reembolso es otro camino del dinero de un miembro a otro, se cobra cada noche del monedero (`HousingDebit.to`) y se embarga de las nóminas después del banco (`EconomyRepository._bank_garnish_in`), sin impuestos: devolver un préstamo no es renta para nadie.
   - Donativos (`EconomyService.donate`): sin IGIC ni Donaciones; desgravan en la renta semanal (`taxes.donation_deduction`).
   - Trabajo (`pala`): las nóminas van por `EconomyService.pay_salary`, que aplica la nómina de `taxes.compute_payslip` (Seguridad Social del trabajador y de la empresa, cotización de solidaridad e IRPF con el tipo estable de la semana) y manda al Estado la retención y las dos cotizaciones; la de la empresa se crea de la nada porque la empresa no existe (decisión del proyecto). Los autónomos cobran con `self_employed=True` (solo IRPF) y pagan la cuota con `charge_self_employed_fee` (la de su puesto, `Position.fee`: los falsos autónomos del reparto pagan la tarifa plana). La lluvia, la valoración de la app, los trienios, la viralidad, el deseo del día y la veteranía (`work.veteran_bonus`: +10 % por rama completada en otros oficios, con tope) solo cambian el bruto del turno; estudiar la oposición no paga. El aval de tus padres (otro favor) no mueve dinero: lo mira `pisos` por `work.parents_aval`. El Bizum de mamá (un favor de la familia de `pala`) va por `mom_bizum` y se devuelve con `repay_mom` desde las nóminas siguientes: tributa como un Bizum entre miembros (exento) y, aunque tu madre no es un miembro y el dinero se crea de la nada, se destruye entero al devolverlo, así que la suma es cero. Los regalos para la familia se compran en la tienda (IGIC) y darlos no mueve dinero. La pensión de jubilación de `pala` va por `pay_salary(pension=True)`: rendimiento del trabajo (art. 17.2.a.1ª LIRPF), IRPF sin cotizaciones (`taxes.compute_pension_payslip`). Es una sola pensión por todas las ramas (`work.pension_amount`, con tope en la base máxima de cotización) y, mientras se trabaja, se cobra la parte de la jubilación activa (art. 214 TRLGSS, `work.active_share`); quien se jubiló antes de la 8.0.0 nunca cobra menos que entonces. Lo cobrado en B va por `pay_undeclared` (sin rastro fiscal) y, si lo pillan, `sanction` y `suspend_imv`. El IMV se reduce con el neto de las nóminas y pensiones de la semana (`imv_after_work`). Quien vuelve tras 5 «años» fuera cobra con `pay_salary(beckham=True)` (art. 93 LIRPF). Los turnos desde Hong Kong van por `pay_foreign_salary`: MPF y salaries tax a la cuenta de Hong Kong (`HK_ACCOUNT_ID`, que no es el Estado ni cuenta en `hacienda`) e IRPF español solo mientras sigue siendo residente, con la exención del art. 7.p y la deducción del art. 80 LIRPF; vivir fuera (`set_residence`) deja sin IMV; el billete está exento de IGIC (transporte internacional). Las stock options de un exit se cobran exentas hasta 50.000 € (Ley 28/2022, por `grant`) y el resto como nómina con `pay_salary`. Las cifras de juego del trabajo (formaciones, cuota de autónomo, billete) se escriben a `WAGE_YAPDOLLARS_PER_EURO` (100 Y$ = 1 €); el IRPF, como toda la renta, a `IRPF_YAPDOLLARS_PER_EURO`. Los sueldos salen de la curva de `work.PayCurve` (receta «Añadir un oficio» de CLAUDE.md) y se calibran con `docs/economia_sim.py`: el puesto 1 debe dejar un neto por turno algo por encima del IMV máximo. Detalle en `bot.services.pala` y `docs/economia-trabajo.md`.
   - Negocios de `pala` (`EconomyService.business`, reglas en `bot.services.business` y casos de uso en `bot.services.negocio`): en la fase 1 son de un autónomo, sin caja propia: todo sale y entra del monedero de su dueño. Las ventas de cada turno las crea la demanda, que no existe: son rendimiento de actividades económicas (art. 27 LIRPF), con criterio de caja (art. 7.2 RIRPF), y retienen a cuenta con el tipo estable sobre el margen del turno (ventas menos el coste de lo vendido) en lugar del pago fraccionado del 20 % (art. 110 RIRPF): una sola vara; les alcanzan el embargo de Hacienda y, después, el del banco (art. 607.6 LEC). Las compras al mayorista pagan IGIC (tipo cero el pan y la leche, el general el resto) y su base desaparece; el autónomo está en el régimen especial del pequeño empresario canario, así que no repercute IGIC y lo soportado es coste: base e IGIC se apuntan como gasto de la actividad (`INCOME_BUSINESS` en negativo, lo que de verdad se paga). Montar paga la tasa de la apertura (al Estado: no hay ayuntamientos) y el acondicionamiento con IGIC (gasto de esa semana, elementos de poco valor del art. 12.3.e LIS por remisión del art. 30 LIRPF: simplificación del proyecto), y deja la fianza de dos mensualidades (art. 36.1 LAU) en el depósito de fianzas, que vuelve al cerrar menos lo que se deba. Cada noche se cobra hasta donde llegue el alquiler del local con su IGIC y la retención del 19 % del casero (art. 100 RIRPF, al Estado; el resto desaparece, porque el casero no existe) y los suministros con su IGIC; lo que no llega es deuda con el casero (no con Hacienda: no se embarga) y a las tres noches el contrato se rescinde. La cuota de autónomos (`charge_self_employed_fee`) es una por persona y semana (`self_employed_fee_paid`), aunque también se sea autónomo en la `pala`. Los impuestos van a `economy_business_tax` para `hacienda`. El grifo de las ventas está topado por el cupo diario de cada barrio y sector y se compensa con el local, el stock, la cuota y el IRPF; se calibra con `docs/negocio_sim.py`. La Seguridad Social de la empresa de los empleados del negocio llegará con la fase 4 (`compute_payslip`): entonces sí la paga alguien.
   - Intereses de la cuenta (`EconomyService.pay_interest`): los paga cada día `bot.cogs.intereses` a todos a la vez (también a los inactivos), sobre el saldo medio ponderado por el tiempo del día anterior, sacado del libro, por tramos y con tope (`bot.services.interest`). Son rendimiento del capital mobiliario (art. 25.2 LIRPF): cada pago retiene el 19 % (art. 101.4 LIRPF) y cada lunes la semana se liquida con la escala del ahorro (`taxes.savings_tax`, arts. 66.1 y 76 LIRPF) a la misma vara que el resto (`IRPF_YAPDOLLARS_PER_EURO`): con el tope diario nunca se sale del primer tramo, así que la liquidación sale a cero y lo retenido es lo que se paga. El bruto se crea de la nada, porque el banco no existe (decisión del proyecto); retención y liquidación van al Estado. No reducen el IMV. El aviso al usuario va por `renta.hint`, que añade la línea de los intereses sin ver (`intereses.hint`) a cualquier resultado con dinero.
   - Loterías (`EconomyService.lottery`): la compra va al Estado sin IGIC (art. 10.1.19º de la Ley 20/1991) y los premios salen del Estado con el gravamen especial del 20 % por encima de 40.000 € por décimo o apuesta (`taxes.lottery_tax`, DA 33ª LIRPF). Si el Estado no llega a un premio, emite deuda pública (`economy_public_debt`), que `hacienda` enseña. No es juego del casino: no pasa por `settle_bet` ni entra en la renta semanal. **El bote de los juegos de bote es una fuente a propósito** (9.25.0, `lottery.guarantee_for`): el Estado garantiza un mínimo que sube cada día sin acertante (`Game.jackpot_floor` y `jackpot_daily`, hasta `JACKPOT_GROWTH_DAYS`) y solo lo paga cuando alguien lo acierta, nunca más del 25 % de su saldo; es el Estado devolviendo parte de lo recaudado, con tope diario (unos 2.000 Y$ entre los cuatro juegos) y unos 78.500 Y$ al mes en el peor caso (`docs/auditoria-loteria.md`). Para que nadie compre el bote, 10 apuestas por persona y sorteo en esos juegos (`POOL_MAX_PER_DRAW`). Las categorías por debajo del bote pagan premios fijos que devuelven entre todas lo mismo que las normas reales (`category_prizes`). Al cambiar esas cifras se vuelve a pasar `docs/auditoria_loteria.py`.
   - Porras (`EconomyService.porra_bet` y `settle_porra`): apuestas cruzadas entre miembros sobre las jugadas de otro (art. 3.c de la Ley 13/2011). Lo apostado espera en el depósito (`PORRA_ACCOUNT_ID`) y la liquidación lo vacía en una sola transacción, con el reparto de `bot.services.porras.split`. Para los apostantes es juego (entra en la retención diaria como `place_bet` + `pay_winnings`). El 10 % de cada apuesta va al Estado como Impuesto sobre Actividades de Juego (`taxes.gaming_tax`, art. 48 de la Ley 13/2011: en la vida real es el 20 % de los ingresos netos del operador, que aquí no existe). El 2 % va al protagonista por derechos de imagen, rendimiento del capital mobiliario (art. 25.4.d LIRPF) con retención fija del 24 % (art. 101 LIRPF, `taxes.image_rights_withholding`). No crea dinero: es un sumidero. El bote no pasa de `POOL_FACTOR` veces lo que se juega el protagonista, que no puede apostar en la suya; nadie puede montársela a sí mismo.
   - Apuestas deportivas (`EconomyService.sports_bet`, `settle_sports_bet` y `void_sports_bet`, reglas en `bot.services.sports`): apuestas de contrapartida a cuota fija (art. 3.c de la Ley 13/2011) sobre partidos de verdad. Es juego, como el casino, pero lo apostado espera en su depósito (`SPORTS_ACCOUNT_ID`) sin tocar el día del casino: al resolverse, apuesta y premio entran a la vez en el día en que se sabe el resultado (art. 14.1.c LIRPF), así la retención y la declaración ven la ganancia neta de esa apuesta aunque se apostara otro día u otra semana. Sin IAJ aparte: el operador es la casa del bot, que no existe, como en los caballos. La anulación (partido sin resultado) devuelve sin tocar el casino ni embargar. El premio se crea y lo apostado desaparece; el sumidero es el margen de las cuotas (`RTP` del 94 %, con la invariante probada de que ningún signo devuelve más), y el tope por partido (`MAX_STAKE`) limita lo que se puede sacar a una cuota que se quedó vieja.
3. **Lo recaudado va a la cuenta del Estado** (`STATE_ACCOUNT_ID`), en la misma transacción, con su propio movimiento en el libro. El dinero de impuestos nunca se destruye, y las devoluciones salen de esa cuenta. `hacienda` debe reflejar cualquier impuesto nuevo.
4. **Mostrar la mordida.** Si el usuario paga o recupera impuestos, el resultado lo dice con una línea pequeña de subtexto (`tax_line`, `gambling_tax_line` o una equivalente) que nombra a `TAX_COLLECTOR`.
5. **Gancho de la Renta en toda acción con dinero.** Toda acción de usuario que gane o gaste dinero y llegue como interacción (botón o slash command) llama a `renta.remind(bot, interaction)` (`bot.cogs.renta`) después de responder a la interacción: avisa una vez por campaña, en un mensaje que solo ve el usuario, de que tiene la declaración pendiente. Si la acción muestra un resultado, añade además `await renta.hint(bot, guild_id, user_id)` cuando no sea `None`. Los comandos de texto no admiten mensajes efímeros; su aviso llega con el primer botón que pulse el usuario.
6. **Embargo de la deuda.** Quien debe a Hacienda paga el 30 % de todo lo que cobra (`taxes.GARNISH_SHARE`, sin mínimo, nómina incluida) hasta saldarla. Un cobro nuevo llama a `EconomyRepository._garnish_in` en la misma transacción, con lo que le llega limpio (después de sus impuestos); en el juego, solo con lo que la jugada sube la ganancia neta del día. No se embargan el IMV, el dinero propio que vuelve (apuestas devueltas, pujas superadas, fianzas, devoluciones), el Bizum de mamá ni lo cobrado en negro. El aviso sale solo con `renta.hint` y la deuda se liquida con el botón de `/renta`. Lo que se debe **al banco** (préstamos vencidos y ejecuciones hipotecarias, `housing_bank_debts`) es otra deuda: se cobra cada noche del monedero y se embarga de las nóminas, las pensiones y las ventas de los negocios de `pala` por tramos del salario mínimo diario, sumando todo lo cobrado en el día (art. 607 LEC: el 607.6 alcanza a los autónomos y el 607.3 acumula las percepciones; `loans.wage_garnish`, en `EconomyRepository._bank_garnish_in`, que llaman `credit_salary` y `business`), después del embargo de Hacienda.
7. **Pruebas.** Cada flujo de dinero nuevo prueba que el libro cuadra con el saldo, que el Estado recibe exactamente lo retenido y, si hay devoluciones, que salen de la cuenta del Estado.
8. **Equilibrio: medir en tiradas.** Una tirada del casino son 100 Y$ y el IMV máximo (1.500 Y$, 15 tiradas por 5 segundos al día) es la vara de medir. Toda fuente de dinero nueva se compara con él antes de fijar cifras:
   - Lo que cuesta más esfuerzo que el IMV (un minijuego, batería, esperar) debe dar algo más que el IMV, pero no tanto que el IMV deje de importar. Referencia: un turno suelto del puesto 1 de `pala` deja entre 1,05 y 1,15 veces el IMV máximo (unas 16 tiradas).
   - Las cifras se calculan con las funciones reales (`compute_payslip`, `week_return`, `imv_after_work`…) en un script, como `docs/economia_sim.py`, no a ojo ni en prosa. Si un cambio mueve sueldos, premios o impuestos, se vuelve a ejecutar y se actualiza `docs/economia-trabajo.md`.
   - Escalar cifras dentro de un impuesto progresivo cambia el tipo, no solo el importe. Por eso el IRPF tiene una sola vara para toda la renta (`IRPF_YAPDOLLARS_PER_EURO`, 250 Y$ = 1 € con la semana como año): lo que cambia el tipo de cada fuente es cuánto paga, no de dónde viene. Una fuente nueva no inventa su propia escala para el IRPF; si sus importes no encajan, se recalibran sus importes.
   - Vigilar el dinero que se crea de la nada (la cotización de la empresa, los premios del bot, los intereses): engorda el Estado y los botes de la lotería. Cada fuente nueva debe tener un sumidero que la compense (impuestos, Patrimonio, tienda, formaciones).
   - **Nada crece sin tope.** Toda fuente de dinero que dependa del saldo (intereses, rentas, cualquier cosa que se reinvierta) va por tramos o con un máximo diario, y el tramo remunerado no pasa del mínimo del Patrimonio. Un 2,5 % diario sin tope duplica el dinero cada 4 semanas y lo multiplica por 8.000 en un año: rompe el equilibrio entre jugar, trabajar e IMV y vuelve trivial cualquier umbral en Y$.
   - **Una sola renta y una sola semana.** La semana es el año fiscal y toda la renta general del miembro (nóminas, pensiones, premios con `pay_income`, casino, pisos, la parte española de Hong Kong) es una sola base. Cada cobro retiene con el **tipo estable** (`taxes.stable_rate`): el mayor entre el tipo de la semana anterior y el de esta semana con lo cobrado, que no baja a mitad de semana (arts. 82 a 87 RIRPF: la empresa retiene con el sueldo previsto del año). La excepción es el **casino**: retiene un 19 % fijo del neto positivo de cada día (`taxes.gambling_day_tax`, el tipo de retención de los premios del art. 101 LIRPF; los días que no pasan de 300 € con la vara del IRPF, `GAMBLING_EXEMPT`, no retienen, como los premios del art. 75.3.f RIRPF), sin mirar el resto de la renta. Cada lunes a las 00:00, el cierre de `bot.cogs.renta` hace la **declaración** de la semana anterior con todo (`taxes.week_return`): sale a pagar, y su dueño la paga al abrirla, entera o fraccionada (el 60 % y el 40 % al final del jueves, art. 62.2 RIRPF), hasta el final del lunes o se cobra entera; lo que no llegue queda como deuda sin recargo (`economy_tax_debts`), o a devolver, y se presenta con el botón de `/renta` durante 4 semanas («4 años»). Así quien gana mucho en el casino paga el lunes lo que el 19 % no cubrió, y quien gana poco lo recupera. La declaración no se adelanta: el aviso del lunes no da la cifra y `/renta` la enseña en un sobre cerrado; abierta, en una carta dibujada (`bot.services.renta_scene`) con cuatro pestañas: el resumen, el desglose por conceptos, el paso a paso con sus artículos y el consejo de los donativos, que se rehace con `taxes.week_return` y no adelanta nada de la semana en curso (`bot.services.renta_report`). Una fuente nueva de renta general no inventa su propia ventana, su propia base ni su propio tipo: apunta su clase de renta (`taxes.INCOME_*`) con `_record_in` y retiene con el tipo estable. La única excepción es la base del ahorro (intereses y ganancias de transmisiones), que la ley separa de la general (arts. 45 a 49 LIRPF).
9. **Lo pendiente sale en `saldo`.** Si algo nuevo deja dinero por pagar, por cobrar o retenido con una fecha (un plazo, una deuda, una puja, un cobro que hay que pedir), su cog lo devuelve como `Pending` (`bot.services.pending`) en su función puente `pending` y `Casino._pending` la añade a la lectura. Cada aviso lleva un `kind` estable: lo cuentan los logros de 🏦 Banco. Lo que el miembro aún no debe saber (la Renta sin abrir) no lleva cifra. El saldo de otro enseña lo mismo que si lo pidiera él.
10. **Solo yapdollars a la vista; el cambio es 1 € = 100 Y$.** Nada de lo que ve un miembro (paneles, botones, menús, escenas, avisos, logros, eventos de `pala`, frases de ambiente) lleva euros: la moneda del juego es el yapdollar y las cifras se escriben con `format_amount` (`1.234 Y$`). Una cifra que el juego cobra, paga o aplica se enseña con su valor de verdad en Y$, sacado de su constante o su función (`format_amount(staff.FINE_PER_WORKER)`, `taxes.vacant_rental_deduction`), nunca copiada a mano ni con el euro entre paréntesis. Una cifra en euros sin equivalente en el juego (una broma, un evento, una ley que se cita y no se aplica) se pasa a 1 € = 100 Y$: un café de 1,50 € son 150 Y$. Los euros solo se quedan en el código (las constantes `*_EUR`, comentarios y docstrings que citan la ley), en la documentación para quien programa (README, FUNCIONALIDADES, `docs/`) y en los nombres propios (Euromillones, Eurovisión). Las escalas internas con las que se calibran las cifras (precios a 10 Y$ el euro, nóminas a 100, IRPF a 250) no se enseñan: deciden cuánto vale algo, no cómo se escribe.

### Tienda: surtido de serie y objetos que se usan

- El surtido de serie vive en `services/shop_catalog.py` y lo que hace cada objeto al usarlo, en `services/shop_uses.py`. Un artículo nuevo es una fila en `CATALOG`; su `key` no se cambia nunca (es lo que une el artículo de cada servidor con el surtido y lo que cuentan los logros). Entra solo en todos los servidores en la siguiente apertura de la tienda; retirar un artículo de `CATALOG` no lo quita de los servidores, que siguen teniéndolo como «De la casa». Cambiar el precio de un artículo que ya existe no llega solo a los servidores que lo tienen: se apunta en `REVISED_PRICES` su precio de antes, y la siguiente apertura de la tienda le pone las cifras nuevas (precio, nivel, existencias y descripción) si un administrador no lo ha cambiado a mano.
- **Dos ejes, una pregunta cada uno.** Todo artículo se clasifica por **tipo** (`Kind`: rol, potenciador, objeto, mascota), que dice **qué hace** y da las pestañas del escaparate, y por **pasillo** (`AISLES`), que dice **de qué va**: el tema o el origen (la Moncloa, Canarias, Hong Kong, la España de siempre…), nunca la función. Un potenciador de Moncloa va en Moncloa, no en un pasillo «de potenciadores»: eso ya lo dice la pestaña. Lo funcional se enseña como etiqueta sacada de los datos del artículo (se usa, 🍽️ se come, limitado, nivel mínimo). Así se disolvieron en 2026 los dos pasillos de función que había (Ultramarinos y la Farmacia de guardia).
- **Ficha de alta de un artículo nuevo**, en este orden:
  1. Tipo por lo que hace. Un tipo nuevo solo si el artículo tiene estado o comportamiento propio que los demás no tienen (como las mascotas).
  2. Pasillo por su tema, leyendo `Aisle.theme`. Si no encaja en ninguno, primero se mira si encaja en el tema de otro; un pasillo nuevo necesita al menos `MIN_AISLE_SIZE` (8) artículos a la venta y al menos uno que haga algo: que se use desde la mochila, que tenga efecto con solo tenerlo (las herramientas de `pala`, los prismáticos y la libreta de la porra) o que se dé desde `pala` (los regalos para la familia, `work_catalog.GIFTS`, con las mismas claves que en `CATALOG`). El desplegable de pasillos admite 23 (25 opciones menos «Todos» y «De la casa»).
  3. Precio en tiradas, IGIC real justificado (ver «Dinero, impuestos y la Renta») y nivel mínimo si cuesta 100.000 Y$ o más.
  4. Si se come, `food=True` (las mascotas se lo comen); si se usa, su `Use` y su logro; si es una especie, va en `services/pets_catalog.py` y el artículo se genera solo.
  5. Las claves de artículo y de pasillo no se cambian nunca. Un pasillo que se vacía va a `RETIRED_AISLES` con el que hereda sus compras (para los logros de pasillos); la clave retirada no se reutiliza. Añadir un pasillo sube la meta de «Me conozco todos los pasillos»: avisarlo en la PR.
  `tests/unit/test_shop_catalog.py` comprueba los puntos 2, 4 y 5 (`test_ficha_de_alta_de_cada_pasillo` y siguientes).
- Cada artículo lleva el tipo de IGIC que le tocaría en la vida real y, si es caro (100.000 Y$ o más), un nivel mínimo. Precios a la escala general (10 Y$ = 1 €) y medidos en tiradas, como el resto de la economía.
- **Títulos** (`CatalogEntry.title`, con `_title`): objetos que se lucen junto al nombre en `perfil`, `fortunas` y `ranking`, uno a la vez, elegido en la mochila. Son la manera de que gastar se vea: un capricho caro que nadie ve no anima a ahorrar. Un título nuevo va en el pasillo de su tema, uno por persona; si cuesta 100.000 Y$ o más, con nivel mínimo, y los más caros, únicos o numerados para que se compita por ellos. Nada de nombres con género («Marquesado», no «Marqués»): el título es la dignidad, no la persona. No dan dinero ni XP, y no entran en la caja botín ni en los regalos de las mascotas. Otro cog que enseñe nombres lo pide con `shop.title_of(bot, guild_id, user_id)`, que sale de memoria.
- **Skins** (`services/skins.py`): cambian el aspecto de una mesa del casino (tapete, baraja, moneda…) y nada más. Nunca tocan probabilidades, pagos ni tiempos. Hay dos registros: `GAMES` (los juegos que las admiten, con sus parámetros de serie) y `SKINS` (cada skin, con los parámetros que cambia). Cada skin genera su artículo `skin_<clave>` en el pasillo de su tema, uno por persona, y se consigue de una de tres maneras: comprándola, con un logro (`achievement`: artículo oculto que la tienda da al desbloquearlo, o al abrir la mochila si el logro ya estaba) o en su temporada (`season`: fuera de sus meses ni sale en el escaparate ni se cobra). Se elige en la mochila o con el botón 🎨 de la mesa (`shop.skin_button`). En las mesas compartidas se ve la de quien abre la mesa, y el mensaje lo dice.
  - **Añadir una skin** a un juego que ya las admite: una fila en `SKINS` con solo los parámetros que cambia (`skins.params` rechaza los que el juego no tiene). Se mira pintada con Node y se comprueba que el resto de la mesa no cambia.
  - **Abrir un juego a las skins:** (1) una fila en `GAMES` con los colores que hoy están escritos en su escena; (2) la escena lee `meta.skin` en lugar de esos colores, con los mismos de serie si no llega, y repinta lo que guarde entre partidas si cambia `meta.skin.key`; se comprueba que **la de serie sale idéntica píxel a píxel** a la de antes; (3) el cog pide `shop.skin_params(bot, guild_id, user_id, juego)` y se lo pasa al dibujo; (4) si el juego pinta antes del clic, la clave de la skin entra en la clave del plan, o saldría el GIF con el tapete viejo; (5) el botón 🎨 va en la mesa si cabe (Discord admite 25 botones; en la ruleta, las columnas pasaron al formulario de 🎯 Números para dejarle sitio) y en las mesas compartidas el mensaje nombra la skin de quien abre. Pillow no conoce las skins: si se dibuja con él, sale la de serie, y no hace falta tocarlo. La ruleta es el ejemplo completo.
  - **Tapetes:** las mesas con fieltro (ruleta, autobús, bacará, dados, moneda, pollo, guerra, blackjack, póker y backgammon) son un juego de skins cada una, del grupo `tapete` (`Game.group`). Una skin del grupo se compra una vez y vale en todas, y cada mesa lleva la suya (lo puesto va por mesa en `shop_skin_worn`); una skin con la clave de una mesa es un tapete solo de esa mesa. El 🎨 de cada mesa deja elegir y comprar (las que se venden y no tienes salen con 🛒 y abren la caja). Cada escena carga `assets/tapete.js` con `<script src="../tapete.js">` (Node y Chromium lo leen igual), toma los colores con `Tapete.felt(meta.skin, los_suyos)` y pinta el dibujo con `Tapete.pattern`; con la skin de serie usa sus colores de siempre y sale idéntica píxel a píxel. Un dibujo nuevo es una función en `PATTERNS` de `tapete.js` y una skin con su `pattern`. Si el escudo de una bandera tapa algo de una mesa, la escena le dice dónde va (`[x, y, escala]`), y un texto claro sobre el fieltro se contornea con `Tapete.outline`. Una mesa nueva con fieltro entra igual.
  - **Skins propias** (`Skin.custom`): el dibujo es una imagen que sube su dueño con `pieles` (una por persona y skin, en `shop_skin_images`). La imagen es entrada no confiable: pasa siempre por `services/skin_images.prepare` (formato real, tamaño, píxeles, EXIF fuera, JPEG). `skins.params` la manda en `image` y mete su resumen en `key`, así cambiarla repinta y tira lo pintado antes del clic. Una escena que pinte `image` la espera en su `setup` (`await Tapete.ready(meta.skin)` en las de fieltro), porque cargar una imagen es asíncrono en Node y en Chromium. Su dueño y los administradores la cambian o la quitan; no hay revisión previa. Para abrir otro juego a las imágenes propias (el dorso de las cartas): una skin `custom` en su juego, su `GAMES` con `image` en los parámetros de serie y su escena pintándola.
  - **`pieles`** junta todas las skins de un miembro leyendo los registros, así que una skin o un juego nuevos salen solos; no se le añade nada a mano.
  - Ninguna skin sale en la caja botín vieja ni en los regalos de las mascotas. Las cajas por niveles (abajo) sí pueden dar, muy rara vez, un tapete de los que se compran.
- Las herramientas de curro (pasillo 🛠️ Ferretería del curro) no se usan desde la mochila: con tenerlas, `pala` las aplica al minijuego (`services/work_tools.py`, con las mismas claves que en `CATALOG`; una prueba comprueba que coinciden). No pagan nada: suben la nota y, con ella, el sueldo. Una herramienta nueva se calibra igual que un sueldo: lo que sube el bruto de un turno frente a lo que cuesta.
- Los muebles del vacacional (pasillo 🛋️ Muebles del vacacional) funcionan igual para `pisos` (`services/housing_furniture.py`, mismas claves): el cierre de cada noche pregunta a la tienda qué tiene quien decide cada vacacional (`shop.owned_keys`) y suben la nota de las reseñas, con un tope entre todos. Como no pagan nada directamente y valen para siempre, se quedan fuera de la caja botín y de los regalos de las mascotas (su valor esperado pasaría del precio de la caja).
- **Escaparate, carrito y lista de deseos** (`bot.cogs.shop_front`): el escaparate es una lista compacta (`compact_line`) con un desplegable que abre la ficha de cada artículo; con un botón por artículo solo cabían 5 por página (Discord admite 40 componentes por mensaje). Toda compra, de una unidad o de un carrito, pasa por `Tienda.complete_cart`: todo o nada en una transacción (`ShopRepository.reserve_cart` mira cada unidad con las mismas reglas que una compra suelta), con una venta y una factura por unidad; solo un rol que Discord no deja dar después de cobrar se devuelve aparte. Lo que impide comprar algo se mira en un solo sitio (`Tienda.check_line`, que usa `ineligibility`, lo mismo que la transacción). La lista de deseos es pública y sus avisos son lo único que el bot manda por mensaje privado (`Tienda.whisper`): solo de lo que cambia (`shop_wishlist.wish_news`), juntos en un mensaje por persona y servidor y con 🔕 para silenciarlos. Un aviso nuevo es una marca más en `wish_state`. Cualquier otro mensaje privado es una excepción que se decide aquí antes de escribirlo.
- **Qué se vende en el Rastro** (`rastro.untradeable`): los coleccionables (`objeto`, títulos incluidos) y los tapetes de las mesas con fieltro que se compran. No se venden mascotas, roles ni potenciadores, ni las skins que no son tapetes, ni las que se ganan con un logro, son de todos o llevan una imagen propia. Un tipo o una skin nuevos deciden ahí si se venden. Mientras algo está en un puesto, la mochila lo tiene a nombre de `MARKET_ACCOUNT_ID`: no se usa, no se luce y no cuenta en el patrimonio de nadie. Cuando un objeto sale de una mochila, `shop.refresh_worn` le quita el título o la skin a quien lo llevaba. El **Monte de Piedad** del panel de `vender` acepta lo mismo salvo lo que no salió de la tienda y lo numerado o de edición limitada (`monte.refusal`); lo que se le vende o se empeña queda a nombre de `PAWN_ACCOUNT_ID`, con las mismas consecuencias que un puesto del Rastro.
- **Cajas por niveles** (`services/lootboxes.py`): cartón, regalo, maletín y cofre, más tres de temporada. Se compran con IGIC; abrirlas no mueve dinero. Cada una devuelve de media ~95 % de su precio a valor de catálogo (`expected_value`, lo comprueba una prueba): abrir cuesta casi lo mismo que comprar. Sacan piezas que solo salen en cajas, en colecciones de 8 (de 6 las de temporada) con rareza de Común a Mítica, y el maletín y el cofre, muy rara vez, un tapete comprable que no pase de su nivel. Las piezas se venden y se cambian en el Rastro. Se ganan gratis: una de cartón cada `FREE_BOX_PLAYS` jugadas del casino de `FREE_BOX_MIN_STAKE` o más y una de regalo cada `FREE_BOX_LEVELS` niveles. Una colección o caja nueva se añade ahí y la prueba del retorno tiene que seguir pasando. La caja botín vieja ya no se vende (`RETIRED_ITEMS`), pero quien la tiene la abre.
- Usar un objeto **no mueve dinero**. Si algún día un uso diera o quitara Y$, entraría en las reglas de «Dinero, impuestos y la Renta» como cualquier otra fuente. La caja botín y los regalos de las mascotas dan objetos de existencias ilimitadas, nunca dinero ni unidades numeradas.
- Las frases de un uso son plantillas con `{who}`, `{target}`, `{item}`, `{collector}` y los huecos de `pools`; `tests/unit/test_shop_catalog.py` las arma todas con varias semillas y falla si queda un hueco sin rellenar. Un uso contra alguien menciona solo a esa persona (`AllowedMentions(users=[…])`); el megáfono no menciona a nadie.
- Cada uso nuevo suma `shop_used_<clave>` y cuenta para «Lo he probado todo» (la meta es el número de usos, así que sube sola). Si tiene un desenlace raro, que tenga su marca (`flag`) y su logro.

### Mascotas y cameos

- Las especies viven en `services/pets_catalog.py` (personalidad, frases, trucos y un detalle de juego pequeño como mucho) y las reglas en `services/pets.py`. Una mascota es una fila de la mochila de tipo `mascota`; su estado (nombre, vínculo, cuidados) va en `repositories/pets.py`. Se adoptan en la tienda (una de cada especie por persona) o aparecen solas (`Species.spawn`); estas van en el catálogo de la tienda ocultas (`visible=False`) y no se venden aunque un administrador las enseñe.
- Perros, gatos y hurones no se venden: se adoptan con «tasa de adopción» (art. 56 de la Ley 7/2023). Todas pagan IGIC al tipo general.
- **Lo de edición limitada no se come.** El menú de comida nunca ofrece un artículo con existencias contadas ni una unidad con número de serie, tampoco a las que comen de todo (`diet="todo"`): no se puede volver a comprar y se perdería sin querer.
- **Cuidar suma, descuidar no resta.** El vínculo solo sube, con un cupo diario por cuidado y una espera entre cuidados. Lo que da es pequeño a propósito: hasta +5 % de XP (`xp_bonus`) y algún regalo del colmado. La razón de tenerlas es su personalidad, no los números. Cuidar no mueve dinero.
- **Cameos: toda funcionalidad nueva que enseñe un resultado a un miembro deja hablar a su mascota.** Si el resultado lleva dinero, ya llama a `renta.hint(bot, guild_id, user_id, moment)`: basta con pasarle el `Moment` (en el casino, `pets.bet_moment(stake=..., net=..., balance_after=...)`; fuera del casino, `Moment(Event.X)`). Si no lleva dinero, llama a `mascotas.cameo(bot, guild_id, user_id, Moment(Event.X))` (`bot.cogs.pets`) y añade la línea si no es `None`. Un momento nuevo es un valor nuevo de `Event`, con sus frases genéricas en `GENERIC_LINES`; las especies pueden tener frases propias para él. Sin `moment` la mascota habla de dinero en general y no aparece ninguna nueva.
- Una especie nueva tiene frases para los tres ánimos (`good`, `bad`, `neutral`), tres trucos, rareza y, si aparece sola, una pista (`Spawn.hint`) y su logro. Sin adjetivos con género en las frases: el nombre lo pone el dueño. `tests/unit/test_pets.py` arma todas las frases de todas las especies en todos los momentos.

### Personalidad: frases y fuentes de ironía

**No todo lo que escribe el bot es una broma.** Esto vale para todo: menús, tienda, juegos, logros, anuncios y frases de Jovani. El bot tiene humor, pero el humor es el condimento, no el plato. Un texto normal, claro y bien escrito vale tanto como un chiste, y es lo que hace que los chistes se noten. Si todo es una broma, ninguna hace gracia y el bot cansa.

- **Lo que informa va en serio.** Menús, botones, ayudas, reglas de un juego, precios, cifras, errores, avisos, confirmaciones y descripciones de lo que hace un artículo o un logro se escriben normales: qué pasa, qué hacer y cuánto. Sin chiste para rellenar. La broma, si la hay, va aparte (una frase de Jovani, un nombre) y nunca tapa la información.
- **Bromas espaciadas.** En una lista de frases que el bot elige al azar, al menos la mitad son normales: celebran, animan o cuentan lo que ha pasado sin referencia graciosa («Buena mano.», «Te quedas a cero; mañana hay más.»). Las bromas se reparten entre ellas, no van todas seguidas ni en todos los mensajes de una misma jugada.
- **Calidad antes que cantidad.** Una lista de frases no tiene cupo ni mínimo. Se mete la broma que sea buena y se deja fuera la que solo cambia el nombre de otra. Variado, con cariño y sin repetir la misma broma con otras palabras. Si un texto que se repite a menudo sale siempre igual, se convierte en una lista de frases (con frases normales y alguna broma) y se elige al azar.
- **Humor de adultos.** El servidor es +18 y está verificado: valen las bromas de adultos, los dobles sentidos y las palabras fuertes (tacos incluidos) cuando suman gracia. Los límites de siempre no cambian: nada contra pueblos, etnias, religiones ni colectivos, ni insultos de ese tipo; nada contra personas reales que no sean figuras públicas, ni contra miembros del servidor que no han pedido la broma; y nada sexual que no sea entre adultos.
- **Herramientas serias, sin bromas.** El panel de moderación `admin` (cog `Moderation`) y el resto de comandos de administración, la telemetría y los avisos de novedades son sobrios: ni bromas ni coletillas.

**Variedad de temas.** En octubre de 2026, `docs/auditoria_frases.py` contaba 576 menciones de Sánchez y el PSOE, más de tres veces que la siguiente fuente, y todas las fuentes contadas eran políticas. Cansa, y no por la política: por tirar siempre de lo mismo. A partir de ahora:

- **Todas las fuentes tienen el mismo protagonismo.** La política es una más, al mismo nivel que el cine, el deporte o la cultura friki: ni la principal ni apartada. ### Logros

**Cada funcionalidad del bot tiene logros asociados.** Una funcionalidad nueva no está terminada hasta que tiene los suyos en el catálogo (en su propia categoría o en una existente) y los alimenta. Si se cambia una funcionalidad, se revisan sus logros en el mismo cambio. Excepciones: los comandos de administración y las utilidades internas (`ayuda`, `latencia`).

**Muchos logros.** Nunca hay que cortarse: cuantos más, mejor. Una funcionalidad con tres logros se queda corta; ninguna categoría baja de una docena y los juegos y sistemas grandes (cada juego del casino, trabajo, tienda, banco, loterías) pasan de cuarenta. **Nombre con gracia, descripción neutral.** El nombre de un logro es siempre un juego de palabras o una broma ligada a lo que pide («Ícaro y el sol» por perder un Crash que iba a ×10, «Rocky Balboa del corral» por 250 KO): nunca literal ni soso («Cien partidas», «Diez victorias»). **Prohibida la comparación de relleno** «X, como [referencia]» («Insomne, como Sánchez con Podemos», «Viral, como un bulo en Telegram»): no es un juego de palabras, es una referencia barata pegada detrás. La gracia tiene que estar en el propio nombre («Sobrecogedor» por aceptar sobres, «Kikirikó» por mil KO). Las frases hechas que ya llevan «como» («Como Pedro por su casa», «Terco como una mula») sí valen. La misma muleta con otra forma tampoco: «X, versión Y», «X, edición Z» o «X (coletilla)» con la broma metida entre paréntesis detrás. El paréntesis vale solo si es el remate que da la vuelta al nombre («Entregado (sin entregar)», «Multiservicios (sin servicios)»). La descripción, debajo, dice en claro y en neutro qué hay que hacer y cuánto, sin broma ni coletilla detrás. Las referencias de los nombres se reparten entre todas las fuentes de «Personalidad» (cine, series, cultura friki, deporte, política, refranes…), todas al mismo nivel, y manda la gracia del nombre: puede tirar de un tema que no tenga mucho que ver con el logro. Un logro que no se entiende o que repite la broma de otro se rebautiza: se cambian el nombre y la descripción, nunca la clave (`key`), que es lo que guarda quién lo tiene.

**Qué logros tiene que tener cada funcionalidad.** Al diseñar los de algo nuevo, o al repasar los de algo que ya existe, se piensa en todas estas familias y se meten todas las que encajen:

- **Escalones de cada contador:** el primero se consigue al probarlo (meta 1, Común) y luego suben con metas redondas (10, 100, 1.000…) hasta Legendario o Mítico. Siempre de menor a mayor meta y sin bajar de rareza.
- **Lo más grande y lo más pequeño:** máximos de una sola vez (mayor premio, mayor multiplicador, racha más larga, más cartas, mensaje más largo) y mínimos ridículos (apostar 1 Y$, cobrar a 1,10x, plantarse con 11).
- **Suerte rara:** lo que pasa poco (tres sietes, el 00, el GRAND, el Gordo). Su rareza sale de la probabilidad real, no a ojo.
- **Mala suerte y fracasos:** perder justo antes de ganar, quedarse a cero, pisar la mina en la primera, que te atropellen en el último carril. Suelen ser los más graciosos.
- **Colecciones:** un logro con varias condiciones por hacer todas las variantes (todos los juegos, todas las dificultades, los 38 números, los seis vehículos, todas las loterías, todos los tipos de risa).
- **Secretos:** las bromas, las cifras con guasa (666, 69, 42, 13:37) y las situaciones absurdas van como secretos (`???` hasta conseguirlos). Más o menos uno de cada seis logros es secreto.
- **Fechas y horas:** madrugada, siesta, horario de oficina, fin de semana, Nochevieja, Reyes, el Día de Canarias, el Pino, Halloween, los Inocentes, el viernes 13. Basta con estar ese día: son Comunes o Raros, nunca más.
- **Rachas de calendario:** días seguidos haciendo algo. 7 días, Raro; 30, Épico; 100, Legendario; un año, Mítico.
- **Mascotas:** si la funcionalidad enseña un resultado, la mascota activa puede salir en él (ver «Mascotas y cameos»); si hay un momento que merezca una mascota que aparece sola, mejor.
- **Social:** lo que se hace a otros o con otros (reírse de alguien, felicitar, Bizum, cadenas de risas, ser el último en saltar).
- **Fiscalidad:** todo lo que mueve dinero tiene logros de Hacienda (primera retención, tramos, gravámenes, devoluciones), con `story` cuando hay una norma real que contar.
- **Coleccionista (metalogros):** contar logros por total, rareza, secretos, categorías tocadas y completadas, puntos y Y$ cobrados. Salen de los logros ya conseguidos (`meta_stats`), nunca de contadores guardados, y solo cuentan los normales para que no se desbloqueen unos a otros sin fin.

**Detectar lo que se escribe.** Del texto de un mensaje solo se miran propiedades y se olvida; nunca se guarda. Lo que necesita contexto del canal (monólogos, ecos, cadenas de risa) va en `ChatTracker`, que solo guarda un hash del último mensaje y está acotado en memoria. Las risas se reconocen en `analyze_laugh` de todas las formas posibles: jaja, jsjs, ajaj y «ja ja ja»; haha, lol y lmao; xd; emojis (😂, 💀 y los personalizados tipo `:kekw:`); aporrear el teclado; kkkk, mdr, wwww, ㅋㅋ y 哈哈; y frases como «me meo» o «lloro». Una forma nueva de reírse se añade ahí, con su prueba, y se comprueba contra las palabras más usadas en español, inglés y portugués para que no salten falsos positivos (como «jauja»). Lo mismo para cualquier detector de palabras: probar que no choca con palabras normales (`podemos` no es Podemos, `nos` no es `ños`).

El menú de logros (botón 🏆 de `perfil`) admite 25 opciones (Resumen y 24 entradas), el máximo de un desplegable de Discord. Hay cuatro grupos que ocupan una sola entrada cada uno y abren sus secciones con un segundo menú: 💬 Chat (`CHAT_GROUP`), 🎙️ Voz (`VOICE_GROUP`), 🎰 Casino (`CASINO_GROUP`) y 🪏 Trabajo (`WORK_GROUP`). Cada sección es una categoría con `group=...`. Un juego nuevo del casino añade su sección en 🎰 Casino (como 🐔 Pollo o 🎫 Porras); algo nuevo de texto o de voz, en su grupo. Discord admite 25 opciones por desplegable: un grupo con más de 24 secciones (el casino, desde ⛏️ Pico) las reparte en dos desplegables, uno debajo del otro (`SectionSelect`, `SECTIONS_PER_MENU`). Las apuestas deportivas (⚽ Deportes) van como entrada propia del menú principal, junto a 🎟️ Loterías. El logro «Peña polideportiva» pide una porra en cada juego que las admite y se amplía solo con cada juego nuevo. Una categoría puede tener tantos logros como haga falta: si no cabe en un embed (4.096 caracteres), la vista de logros la parte en hojas con ◀ y ▶. Aun así, si una categoría mezcla dos temas, mejor dos secciones (como 😂 Risas y 🤡 Hacer reír). Una categoría secreta (`Category.secret`, hoy solo 🎸 Robuso) no sale en el menú ni en el resumen hasta que el miembro consigue uno de sus logros, y va aparte del total y de Coleccionista (`APART`), porque muchos de sus logros solo los puede conseguir una persona; sus descripciones no dicen cuáles son solo suyos, para que quede la duda. Lo que se puede repetir a propósito (decir una palabra, mencionar) cuenta una vez al día por persona y lo dice la descripción («días distintos»). Cualquier otra funcionalidad nueva entra en una categoría existente afín (como la cuenta remunerada en 🏦 Banco, con el Bizum) o en una entrada nueva mientras quepa; `tests/unit/test_achievements.py` comprueba el límite.

`pala` los alimenta con `work_stats` (turnos) y con estadísticas sueltas desde el panel y los eventos. Todos sus logros van en el grupo 🪏 Trabajo, una sola entrada del menú: la sección 🪏 General, 👷 Oficios y una sección por oficio con trucos propios (🍽️ Hostelería, 🏥 Sanidad, 💻 Oficina, 🛵 Reparto, 🗂️ Funcionariado, 🤳 Influencer), 🇭🇰 Hong Kong y 🏪 Negocio, que alimentan los negocios con `business_stats` (cada turno) y con estadísticas sueltas al montar, comprar, cambiar precios, cerrar y en cada noche; la plantilla, con las `staff_*_stats` (contratar, despedir, subir el sueldo, hacer fijo, cursos, sus turnos y la noche). Un oficio nuevo con trucos propios añade su sección en el grupo (`group=_WG`).

Chat y voz, además de lo de siempre: enlaces por sitio (`LINK_SITES`), adjuntos por tipo (solo el tipo MIME y el nombre del archivo, nunca el contenido), notas de voz y encuestas; cifras y horas con guasa; temas con guasa (`FUNNY_TOPICS`: solo temas que tengan gracia, no cualquier tema, y cada patrón con su prueba contra palabras normales); el ping-pong, las respuestas rápidas y romper silencios en `ChatTracker`; reacciones con contador propio (`REACTION_EMOJIS`, una por persona, emoji y mensaje); y escribir desde la llamada. La voz cuenta cada día con llamada (`voice_day_AAAAMMDD`, de donde sale la racha en `with_derived`, que así sobrevive a los reinicios), los minutos con cada persona (`voice_with_<id>`: personas distintas y compañero más habitual), quién abre una sala que se llena, quién cierra la llamada y a qué se juega en llamada (`VOICE_GAMES`, por el nombre de la actividad; necesita el intent de presencias). Los 🎭 Personajes son logros combinados que cruzan estadísticas de chat, voz y el resto del bot.

Música, imagen (`magik` y efectos), sonidos de entrada y `babel` los alimentan con `achievements.note_for(bot, responder, delta)`, que saca servidor, miembro y canal del `CommandResponder`. Las risas se detectan en `analyze_laugh`: una forma nueva de reírse se añade ahí, con su prueba y comprobando que no choca con palabras normales.

Cómo alimentar los logros (`bot.cogs.achievements`):

1. **Juegos del casino:** al terminar cada jugada, y después de enseñar el resultado (un aviso antes destriparía la tirada), llamar a `achievements.casino_play(bot, guild_id, user, canal, delta, net=neto)`. Justo después, `apuestas.record(bot, guild_id, user, game=..., stake=..., net=..., balance_after=..., tax=...)` (`bot.cogs.apuestas`) con las mismas cifras de `casino_stats`, para que la jugada salga en las estadísticas del casino. Un juego nuevo añade su clave a `GAMES` en `services/casino_stats.py` (la misma que usa como motivo en el libro). `apuestas.record` también le pasa cada jugada a los logros (`casino_record_stats`): jugadas totales y por juego, juegos distintos y las fechas de cada juego (madrugada, viernes 13, Día de Canarias, Nochevieja) y del casino entero, así que un juego nuevo tiene esos contadores sin más; sus logros de fecha se añaden a la lista de `_build_catalog` si el juego no los tiene ya con estadística propia. Un juego nuevo en `GAMES` sube la meta de «Pasaporte del casino sellado» y de los «todos los juegos» de Coleccionista del casino: avisarlo en la PR. Con eso y `apuestas.record` ya tiene porras (`bot.cogs.porras`): `record` le pasa cada jugada a `porras.observe` y las propuestas genéricas solo miran apuesta, premio y saldo. Si el juego quiere propuestas propias, manda sus datos en `details` (como `boom` en minas) y añade la propuesta a `services/porras.PROPOSITIONS` con `games` y `details`; si la partida dura (no se resuelve en el mismo clic), manda también `started`, para que una partida empezada antes del cierre de apuestas no cuente. Un juego que no admita porras va en `EXCLUDED_GAMES`, como el crash. `delta` sale de `casino_stats(...)` más las estadísticas propias del juego, calculadas con una función pura en `services/achievements.py` (como `roulette_stats` o `blackjack_stats`).
2. **Otras acciones:** `achievements.track(...)` si el aviso debe salir ya (IMV, renta, subir de nivel) o `achievements.note(...)` si basta con la escritura de cada minuto (cosas frecuentes como mensajes o reacciones).
3. **Nunca romper al que llama:** estas funciones no lanzan y no hacen nada si el cog de logros no está cargado.
4. **Rarezas:** la rareza dice cuánto le cuesta a un miembro activo conseguirlo: Común, tres días o menos; Raro, hasta dos semanas; Épico, hasta dos meses; Legendario, hasta ocho meses; Mítico, más (o suerte de una entre decenas de miles). Reglas que salen de la auditoría de `docs/auditoria-logros.md`:
   - Dentro de una misma estadística, un escalón más alto nunca es más común. Los nombres no se repiten. Las dos cosas las comprueba una prueba.
   - Para un logro de suerte de un juego del casino, la rareza sale de `docs/auditoria_logros.py`, que simula jugadores con el código real. Al añadir logros de suerte o tocar las probabilidades de un juego se vuelve a ejecutar y se actualiza el `.md`.
   - Lo que el jugador puede forzar a propósito (apostar una cifra, cobrar pronto, plantarse, rachas de victorias cobrando a 1,01x, probar todos los juegos) es Común o Raro aunque parezca difícil: es una decisión, no un mérito.
   - Lo que depende de la apuesta (ganar 100.000 Y$ de golpe) se mide por lo que apuesta un jugador normal, no por el máximo.
   - Lo que pide tiempo de calendario (rachas, días cobrando) no puede ser Común aunque no cueste nada: se mide en los días que hay que esperar.
   - La rareza fija el premio (50, 200, 750, 2.500 o 10.000 Y$), así que inflarla también infla la economía.
5. **Catálogo:** un logro nuevo es una fila en `_build_catalog`. Los escalones nuevos de una estadística van después de los que ya existen en el catálogo (la prueba exige metas de menor a mayor en el orden del catálogo). Si además debe contar algo la primera vez que pasa (como la primera retención de IRPF), se le da un `story`: sale en su aviso y, como cada logro se desbloquea una vez, ese texto también. Los `id` no se cambian nunca (son lo que se guarda). Una estadística nueva debe añadirse al conjunto `PRODUCED_STATS` de `tests/unit/test_achievements.py`, que comprueba que ningún logro dependa de algo que nadie suma.
6. **Umbrales en dinero:** al cambiar la escala de una fuente de dinero (sueldos, premios, apuestas), revisar en el mismo cambio los logros con umbrales en Y$ que dependan de ella; si no, se vuelven triviales. El `id` se mantiene y solo cambian el umbral y el texto.
7. **Al desplegar, cuidado con lo retroactivo:** los logros nuevos que se calculan con lo que ya hay guardado (niveles, mensajes importados, rachas, Coleccionista) los cobran de golpe los veteranos en su siguiente acción. Si son muchos o muy caros, avisarlo en la PR.
8. **Estadísticas por variante:** cuando un logro necesita saber «cuántas distintas» (números de la ruleta, efectos de imagen), se guarda un contador por variante con prefijo (`roulette_hit_17`, `img_fx_magik`) y el recuento se calcula en `with_derived`, sin guardarlo.

### Persistencia

- No introducir una base de datos hasta que exista una necesidad funcional de conservar datos entre reinicios.
- Cuando se añada persistencia, aislarla detrás de repositorios y definir el ciclo de vida de conexiones y migraciones.
- Las operaciones de base de datos deben ser asíncronas o ejecutarse fuera del event loop si el controlador es síncrono.
- Toda conexión a SQLite se abre con `bot.repositories.sqlite.connect`: modo WAL y `synchronous=NORMAL`, para que una escritura no sincronice el disco del NAS ni bloquee las lecturas. Con el diario de serie, cada tirada del casino forzaba siete sincronizaciones del disco y los botones esperaban detrás de las escrituras de cada mensaje del chat. Si se va la luz se pueden perder las últimas transacciones, pero la base no se corrompe. Como cada operación abre y cierra su conexión sin volcar el registro al cerrar, SQLite no lo recicla nunca por su cuenta: `BotClient` lo vacía cada minuto con `sqlite.checkpoint` (`wal_checkpoint(TRUNCATE)`), al arrancar y al apagarse. Sin eso el registro crecía sin fin y cada conexión tardaba más (la tragaperras pasaba de 29 a 60 ms por tirada en 600 tiradas).
- No guardar datos personales innecesarios. Definir retención y borrado cuando el bot almacene datos de usuarios.

### Utilidades y modelos

- `utils/` se reserva para funciones pequeñas y sin estado que sean realmente compartidas; no debe convertirse en un cajón de sastre.
- Modelos y tipos compartidos deben reflejar conceptos del proyecto, no envolver tipos simples sin aportar validación o significado.

### Documentación obligatoria

- Todo archivo de código debe comenzar con una docstring de módulo que explique su responsabilidad. Si un archivo tiene un formato que no admite docstrings, documentar su propósito en el lugar apropiado del propio archivo (por ejemplo, comentarios de configuración) o en la documentación asociada.
- Cada clase y función pública debe tener una docstring que describa su propósito, parámetros relevantes, resultado y errores importantes cuando no sean evidentes por sus tipos o contrato.
- Los comandos y eventos de Discord deben documentar qué hacen, sus requisitos de permisos/intents y cualquier efecto visible o persistente relevante.
- Los comentarios dentro del código deben explicar **por qué** existe una decisión, una restricción o un caso no obvio; no repetir literalmente lo que ya expresa el código.
- Los archivos de configuración deben explicar las opciones no evidentes, los valores aceptados y si una opción es sensible u opcional. Nunca incluir credenciales reales como ejemplo.
- Las pruebas deben indicar mediante nombres descriptivos qué comportamiento o caso límite verifican. Añadir una nota cuando el escenario no se entienda claramente a partir del nombre y el test.
- Mantener README y ejemplos de configuración al día cuando cambien la instalación, el arranque, las variables de entorno, los comandos o el comportamiento operativo.
- La documentación debe ser breve, precisa y mantenerse junto con el cambio que documenta. No aceptar archivos nuevos sin propósito documentado ni cambios de lógica no trivial sin explicación suficiente.
- No añadir comentarios redundantes a líneas obvias: la exigencia es que cada archivo y comportamiento relevante sean comprensibles, no comentar cada instrucción mecánica.

### Versiones

El bot sigue versionado semántico (MAYOR.MENOR.PARCHE), juzgado desde quien usa el bot en Discord, no desde el código. La versión vive solo en `__version__` de `src/bot/__init__.py` (el `pyproject.toml` la lee de ahí) y cada número tiene su entrada en `CHANGELOG.md`.

1. **Cada cambio que entra en `main` sube la versión una vez**, sea un PR, un commit directo o una rama fusionada a mano, y venga de quien venga. Un PR del fork que junta varios cambios sube una sola vez, con el escalón del más fuerte que traiga. Lo que se queda en una rama o en el fork no sube nada.
2. **MAYOR (x.0.0): algo que la gente ya hacía deja de funcionar igual.** Quitar o renombrar un comando, cambiar el prefijo, quitar una funcionalidad (como la hora feliz) o juntar varios comandos en otro (como `perfil`), y cualquier pérdida o reinicio de datos de los miembros (saldos, niveles, logros, inventario) que no se compense. Si el cambio pide avisar al servidor de que ahora se hace de otra forma, es mayor.
3. **MENOR (x.y.0): algo nuevo que se puede hacer o ver, sin romper lo anterior.** Un comando, juego, oficio, artículo de tienda, logros, una opción o botón nuevo, una mecánica nueva, un rediseño visible de una mesa o panel, un ajuste de administración nuevo y un cambio de regla que el usuario nota (como la semana fiscal de la Renta).
4. **PARCHE (x.y.z): lo mismo, pero mejor.** Arreglos, velocidad, memoria, retoques de textos o de animación, ajustes de equilibrio (premios, probabilidades, precios, topes, aunque un rango se encoja), pequeños retoques de usabilidad en algo que ya existía y todo lo interno (pruebas, documentación, despliegue, instrucciones para agentes).
5. **Si duda entre dos escalones, gana el más alto.** Un cambio que mezcla cosas sube por la más fuerte.
6. Al subir MAYOR, MENOR y PARCHE vuelven a 0; al subir MENOR, PARCHE vuelve a 0.
7. **Entrada en `CHANGELOG.md`**, arriba del todo: `### X.Y.Z · AAAA-MM-DD`, una viñeta con el título del cambio (el mismo del PR o del commit) y, si es mayor, otra que empiece por «Rompe:» y diga qué deja de funcionar. La primera versión de cada mayor abre su `## X.x`.
8. **Si al fusionar choca la versión** (dos ramas subieron a la vez), se recalcula sobre la de `main` y se renumera la entrada; nunca dos entradas con el mismo número.

`tests/unit/test_version.py` comprueba que `__version__` es válida, que coincide con la primera entrada de `CHANGELOG.md` y que el historial va de mayor a menor sin repetir números. El escalón elegido no lo puede comprobar una prueba: lo revisa quien fusiona.

## 5. Normas de rendimiento y concurrencia

- No usar `time.sleep`, `requests` ni lecturas/escrituras de archivos bloqueantes dentro de una coroutine.
- Usar `asyncio.sleep` para esperas y clientes asíncronos para I/O. Para trabajo bloqueante inevitable, usar un executor o una alternativa asíncrona adecuada.
- No hacer llamadas de red o consultas repetidas dentro de bucles si se pueden agrupar, reutilizar o almacenar en caché con una caducidad explícita.
- Mantener las tareas en segundo plano identificables y cancelables; cerrarlas durante el apagado.
- Aplicar límites a concurrencia, reintentos y tamaño de lotes. Los reintentos deben respetar `Retry-After` y no multiplicar efectos no idempotentes.
- No crear cachés globales sin política de caducidad y límites de memoria.
- Evitar consultas redundantes a Discord: aprovechar los datos de la interacción y las cachés de la librería cuando sean suficientes.
- Nada de trabajo lento antes de contestar a una interacción (ver «Cogs y comandos»). Los clics que llegan en ráfaga contra un mismo candado se aceptan fuera de él: dentro, cada uno espera al anterior y los últimos pasan de los 3 segundos de Discord.
- El NAS tiene 4 hilos: el trabajo de imagen que no depende del orden va en paralelo (pestañas de `BrowserScene.render`, procesos de Node compartidos de `NodeScene`, que colaboran todos en cada dibujo, cada fotograma de `bot.utils.gif`, que empieza a codificarse mientras Node pinta, PNG de `browser_scene.assemble`). Nada de comprimir o abrir imágenes en el bucle de eventos: va en `asyncio.to_thread`; el informe apunta dónde se para el bucle (sección «Bloqueos del bucle»). Detalle en «Rendimiento en el NAS» de CLAUDE.md.
- Un juego nuevo con animación sigue «Juego nuevo con dibujo» de CLAUDE.md: escena de canvas pintada con `NodeScene.render` (sin repartir a mano), azar repetible por fotograma (nunca `Math.random`), el estado que pasa de un fotograma a otro recreado con `warmup`, los fotogramas tal cual a `local_palette_gif`, imágenes quietas con `asyncio.to_thread`, pintar antes del clic cuando se pueda y ninguna subida de una imagen que ya se ve. Se mide antes y después con `docs/medir_dibujos.py` a 4 hilos.
- Los GIF animados se escriben con `bot.utils.gif` (`shared_palette_gif` si los fotogramas comparten paleta, `local_palette_gif` si van a color completo), nunca con `save(save_all=True)` a pelo: la optimización por defecto de Pillow recorre los píxeles en Python y en el pachinko se comía ~750 ms de los ~870 de una tanda. Los efectos de imagen de los miembros (`services/memes`) son la excepción, porque sus fotogramas vienen de fuera. Una animación de cientos de fotogramas (el pozo de `picar`) se monta por tramos con `GifStream`, que da los mismos bytes que `local_palette_gif` sin tener todos los fotogramas en memoria, y se parte en varios GIF antes del límite de subida.
- Un panel con estado por usuario (como el de `pala`) admite una sola acción en curso: el cog guarda quién está en una (`working`) y rechaza la segunda, porque dos botones de dos paneles pueden llegar a la vez y cobrar dos veces.

## 6. Seguridad y permisos

- El token del bot y cualquier credencial son secretos. Usar variables de entorno o un gestor de secretos del entorno de despliegue.
- Revocar y rotar inmediatamente un token expuesto; no confiar en borrarlo del historial como única medida.
- Solicitar solo los intents y permisos necesarios. Los intents privilegiados deben habilitarse tanto en el portal de Discord como en el código cuando proceda. Para eventos de entrada/salida de miembros se necesita `Server Members Intent`; para la «última vez conectado» del panel `admin`, `Presence Intent` (si falta en el portal, `start_bot` arranca sin él).
- Comprobar autorización en el servidor, no solo ocultando botones o comandos en la interfaz.
- No construir consultas, rutas, menciones ni contenido privilegiado directamente a partir de entrada no validada.
- Desactivar menciones accidentales al reenviar contenido de usuarios cuando corresponda (`AllowedMentions`).
- No registrar tokens, secretos, contenido sensible ni datos personales completos. Preferir identificadores solo cuando sean necesarios para diagnosticar.
- Tratar contenido, adjuntos, nombres y mensajes de Discord como entrada no confiable.

## 7. Errores, logs y observabilidad

- Usar el módulo `logging` de Python y una configuración centralizada; no usar `print` como sistema de logs de producción.
- Incluir contexto útil (comando, servidor o identificador de interacción cuando sea apropiado), sin registrar secretos.
- Capturar excepciones únicamente cuando se puedan manejar, contextualizar o registrar. No usar `except Exception: pass`.
- Los errores esperados deben producir mensajes comprensibles para el usuario; los errores inesperados deben quedar registrados con su traza en los logs internos.
- El apagado debe cerrar el cliente y los recursos compartidos de forma ordenada.
- Telemetría interna (`bot.cogs.telemetry`, `bot.services.telemetry`): cuenta usos, latencias y memoria para decidir mejoras, nunca contenido. Contar es `bot.telemetry.count(...)`, una suma en memoria que se vuelca cada minuto: se puede llamar desde un botón antes de contestar. Comandos, botones, formularios, mensajes, voz, log, dibujos y subidas de archivos a Discord ya se cuentan solos; una funcionalidad nueva solo llama a `count` si hace algo que no pasa por ahí (un bucle propio, un evento distinto). No es una funcionalidad para los miembros: no lleva logros (excepción a la sección 10). Antes de optimizar o de quitar algo, pide el informe (`informe`) y mira `docs/analisis_metricas.py`.

## 8. Pruebas y calidad

- Añadir pruebas unitarias para validación, reglas de negocio y transformaciones con comportamiento significativo.
- Las pruebas no deben requerir un token real ni conectarse a Discord. Aislar API, reloj, red y persistencia mediante dependencias sustituibles.
- Añadir pruebas de integración para interacciones entre componentes cuando exista una frontera relevante.
- Antes de integrar un cambio, ejecutar las pruebas afectadas, el formateador y el linter configurados.
- No afirmar que una funcionalidad está probada si solo se ha verificado visualmente o mediante una ejecución manual.
- Una prueba que crea los cogs a mano (`Slots(MagicMock(), …)`) no reproduce producción. En producción el bot carga los cogs con `load_extension`, que vuelve a ejecutar cada módulo, y solo comparte los cogs reales entre ellos. Todo lo que cruza de un cog a otro (logros, Renta, tienda, niveles) se prueba también con `BotClient` y `INITIAL_EXTENSIONS`, como en `tests/integration/test_cog_bridges.py`.
- Al investigar un fallo que solo pasa en el bot desplegado:
  1. Reproducirlo primero arrancando el bot real: `BotClient` + `load_extension` de `INITIAL_EXTENSIONS` en orden, con `tree.sync` sustituido por un doble. No concluir que «el código está bien» ni culpar al servidor, a Docker o a la base de datos si solo se ha probado con cogs montados a mano.
  2. Desconfiar de los caminos que fallan en silencio: las funciones puente «no lanzan y no hacen nada si el cog no está cargado», así que un fallo ahí no deja rastro en el log. Comprobar con una aserción que la llamada llega al cog y que el dato se guarda (por ejemplo, `profile.stats`), no solo que no hay excepciones.
  3. Si el síntoma es que falta todo (cero estadísticas, ningún aviso) y no solo una parte, sospechar antes del enlace entre componentes que de la lógica del juego.
  4. Una hipótesis se da por buena cuando una prueba la reproduce y el arreglo la hace pasar, no antes.
- Un dibujo de Node lleva una prueba que compara el dibujo repartido entre procesos con el de un solo proceso, byte a byte, y comprueba que se ha repartido de verdad. Un cambio en el camino de dibujo (`node_scene`, `bot.utils.gif`, `assemble`) se da por bueno cuando el GIF y el PNG finales de cada juego salen con los mismos bytes que antes.
- Mantener los ejemplos y la documentación coherentes con el comportamiento implementado.
- Las pruebas usan las constantes del código (`WAGE_YAPDOLLARS_PER_EURO`, `IMV_WORK_EXEMPT`, `SELF_EMPLOYED_FEE`…), no cifras copiadas, para que recalibrar la economía no rompa decenas de pruebas por un número. Si una prueba necesita saldo, lo da con margen.
- El azar se fuerza en la prueba (sustituyendo `random` o pasando la tirada), no se confía en que dos probabilidades distintas den resultados distintos: dos constantes con el mismo valor hacen que la prueba acierte por casualidad.
- Al cambiar una cifra visible (sueldo, precio, umbral, exención), buscarla en README, FUNCIONALIDADES, la Biblia y los textos de los cogs (`grep` de la cifra con y sin punto de miles) y actualizarla en el mismo cambio.

### 8.0. Agentes y subagentes

Para los agentes de IA que trabajan en el repositorio. El agente principal es el que habla con la persona: diseña, reparte, revisa y fusiona. Los subagentes hacen trabajo delegado.

**Qué subagentes se pueden usar.** Solo dos familias de modelos, siempre en la versión más moderna que ofrezca la herramienta (en Claude Code, `model: "haiku"` o `model: "sonnet"` en la herramienta `Agent`, que apuntan a la última versión de cada una). Ningún otro modelo, tampoco uno igual al del agente principal.

- **Haiku: lo rápido y mecánico.** Es el más rápido y barato, y rinde bien cuando la tarea no pide criterio. Para:
  - buscar en el repositorio y resumir qué hay (dónde se usa algo, qué pruebas tocan un archivo);
  - cambios mecánicos y repetitivos con un patrón claro: renombrar, actualizar cifras en README, FUNCIONALIDADES y textos, añadir una estadística a una lista;
  - pasar `ruff` y `pytest` y resumir los fallos;
  - medir o ejecutar un script ya escrito (la auditoría de logros, el calibrador) y devolver las cifras.
- **Sonnet: el código de verdad.** Programa bien, sigue instrucciones largas y aguanta tareas de varios pasos. Para:
  - implementar una pieza acotada con su contrato ya fijado: un dibujo nuevo, un repositorio, una función de servicio con sus pruebas;
  - escribir las pruebas de algo que ya funciona;
  - una refactorización limitada a uno o dos archivos;
  - investigar un fallo concreto y proponer el arreglo.
- **Lo que no se delega:** decidir el diseño, tocar la economía o los impuestos, recalibrar probabilidades, cambiar esta Biblia o el CLAUDE.md, fusionar ramas, resolver conflictos y hacer push. Eso lo hace el agente principal.

**Cómo se usan.**

- **Uno a la vez**, nunca dos en paralelo. Cada subagente arranca sin contexto y, si se cortan varios a la vez (por ejemplo, por el límite de gasto), dejan trabajo a medias en varios sitios.
- **Si Haiku o Sonnet pueden hacerlo, se les delega y el agente principal espera.** No adelanta por su cuenta el mismo trabajo ni otro que lo pise: espera al informe, lo revisa y decide. Se elige el más ligero que pueda hacerlo bien: Haiku si es mecánico, Sonnet si hay que programar.
- **Solo tareas bien acotadas:** qué archivos puede tocar (y cuáles no), las firmas o el contrato que tiene que respetar, cómo se comprueba que está bien y qué tiene que devolver. Si no se puede escribir así en un párrafo, la tarea la hace el agente principal.
- **Siempre bajo supervisión.** El subagente trabaja en su propia copia (`worktree`), parte de la rama de trabajo y no de un `main` antiguo, y hace commit en su rama sin push. El agente principal lee el diff, mira las imágenes si hay dibujo, pasa las comprobaciones y solo entonces fusiona. Lo que el subagente dice que ha hecho no cuenta hasta que el agente principal lo ha comprobado.

### 8.1. Estándar de documentación por archivo

Como mínimo, cada archivo nuevo o modificado debe cumplir lo siguiente:

| Tipo de archivo | Documentación requerida |
|---|---|
| Módulo Python | Docstring inicial que describa su responsabilidad y límites |
| Clase o función pública | Docstring con propósito y contrato; incluir parámetros, retorno y errores relevantes cuando corresponda |
| Lógica compleja o no obvia | Comentario breve que explique la razón, el caso límite o la restricción |
| Prueba | Nombre que identifique el comportamiento probado y el caso relevante |
| Configuración | Comentarios o documentación para opciones no evidentes, valores válidos y secretos |
| Script operativo | Instrucciones de uso, entradas, efectos y requisitos importantes en el propio archivo o documentación vinculada |
| Documentación / ejemplos | Explicar su propósito y mantenerlos consistentes con el comportamiento actual |

La revisión de cada cambio debe comprobar expresamente que no se han añadido archivos sin documentar y que la documentación modificada sigue siendo correcta.

## 9. Configuración mínima prevista

El proyecto podrá requerir estas variables a medida que se implementen sus funciones:

| Variable | Uso | Regla |
|---|---|---|
| `DISCORD_TOKEN` | Autenticación del bot | Obligatoria para ejecutar; secreta y nunca versionada |
| `LOG_LEVEL` | Nivel de logs | Opcional, con un valor por defecto seguro y documentado |
| `DATABASE_URL` | Conexión a datos | Añadir solo si se incorpora persistencia |
| `CASINO_CHANNEL_IDS` | Canales donde se permiten los juegos del casino | Opcional; IDs separados por comas, vacío = cualquier canal |
| `ODDS_API_KEY` | Clave de The Odds API para las apuestas deportivas (`deportes`) | Opcional y secreta; vacía = `deportes` avisa de que no está configurado |

No introducir valores de configuración sin uso. Documentar cualquier nueva variable en `.env.example` y en el README.

## 10. Criterios para aceptar cambios

Una funcionalidad está lista cuando:

1. Cumple el requisito definido y respeta los límites de este documento.
2. Valida permisos, entradas y errores en los puntos adecuados.
3. No bloquea el event loop ni hace trabajo repetido innecesario.
4. Tiene pruebas proporcionales al riesgo y al comportamiento añadido.
5. No incorpora secretos ni permisos/intents que no necesite.
6. Actualiza la documentación y los ejemplos de configuración afectados.
7. Puede arrancar y cerrarse limpiamente en el entorno previsto.
8. Si mueve dinero, cumple las reglas de "Dinero, impuestos y la Renta" (sección 4).
9. Tiene logros asociados y los alimenta, según la sección "Logros" (sección 4).
10. Sube la versión y añade su entrada a `CHANGELOG.md`, según la sección "Versiones" (sección 4).

## 11. Evolución de esta biblia

Esta guía puede cambiar cuando haya una necesidad concreta, pero los cambios de arquitectura, dependencias, almacenamiento, permisos o manejo de datos deben quedar documentados y motivados. No mantener una regla que contradiga deliberadamente el código: actualizar ambos en el mismo cambio.
